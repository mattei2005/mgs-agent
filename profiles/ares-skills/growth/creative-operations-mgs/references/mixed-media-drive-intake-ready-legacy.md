# Mixed-media Drive intake → READY + LEGACY

Use when an authorized request identifies country, vertical and language and asks Ares to apply rules to an image-only, video-only or mixed batch in `UPLOAD MANUAL`.

## Durable execution pattern

1. Resolve the live hierarchy from the configured root and confirm `MGS-AGENTS/CRIATIVOS/UPLOAD MANUAL`; never assume the root ID is itself `CRIATIVOS`.
   - For the Shared Drive root, `files.get(root_id)` can legitimately return the generic file name `Drive` even when `id` and `driveId` are both the canonical Shared Drive ID. Validate the actual Shared Drive name with `drives.get(drive_id)` and require `name=MGS-AGENTS`; use `files.get` for root ID, `driveId` and capabilities. Do not reject a valid root solely because the file-resource name is `Drive`.
2. List current source files with Drive ID, name, MIME, size/checksum, image/video dimensions, `ownedByMe` and `capabilities(canDownload,canEdit,canMoveItemWithinDrive,canTrash,canDelete)`. Key all processing by `source_drive_id`, not filename.
   - For the canonical treat/move flow, require the capabilities actually used: download the raw asset, upload the clean copy, and move the source within Drive. `ownedByMe=false`, `canTrash=false`, or `canDelete=false` do not block processing because the original is preserved rather than deleted.
   - Block only when a required capability is absent or the live API rejects that action. Do not require transfer of ownership by default.
   - If Drive has not populated dimensions or duration yet, download and inspect with `ffprobe` or the media decoder; missing Drive media metadata alone is not a rejection or ownership blocker.
   - **Asynchronous-upload stability gate:** a newly announced batch may appear as empty or grow one file at a time while Drive is still finalizing uploads. Before freezing the inventory or starting any write, poll the direct `UPLOAD MANUAL` parent with bounded waits and compare the complete ordered set of `(source_drive_id, name, size)`, not only the count. Require the same non-empty set in at least three consecutive polls spanning a reasonable quiet window (normally 30–60 seconds). If the set changes, restart the quiet-window count. Also require every item to be downloadable and technically probeable before declaring the batch stable.
   - Never interpret an initial empty listing as “nothing to process” when the request has just been sent. Re-query the live parent and inspect recently created accessible media before reporting a blocker. If the request explicitly names a manager destination, inspect that exact existing folder for recent, unregistered media before asking for a re-upload: uploads may already be there. Reconcile source/destination IDs against inventory and prior completed manifests, exclude previously pending or unrelated neighboring files, and require an unambiguous count/time/name match to the announced batch plus the same stability/probe gates. Record and communicate the actual source parent; never relabel it as `UPLOAD MANUAL`, broaden to other managers or silently choose a subset. When no unambiguous batch is found after bounded checks, report the observed location/count and ask only for the missing source identification, without inventing completion.
   - Managers may upload a container folder beneath `UPLOAD MANUAL` instead of placing media directly in the parent. Inventory and stabilize media recursively by `source_drive_id`. Before moving a source, read back its actual current parent, verify that parent is a descendant of the canonical `UPLOAD MANUAL`, and remove that exact parent when adding the matching `99_LEGACY` parent. Final pending count must also scan recursively; an empty container folder is not a pending creative.
3. Download the stable batch and build compact visual evidence:
   - one labeled image contact sheet;
   - for each video, a labeled strip with frames near 20%, 50% and 80%; inspect a final frame separately if the dominant claim remains unclear.
4. Classify each asset from visible evidence: `IMG|VID`, dominant `ANGLE`, `PV|NV|PH|NH`, placement and exact operation code. Square/feed 1:1 uses `PH|NH` for final naming. For Brasil + CAR + Português without Portugal context, use `CAR_BR_BR`; use `PT` only when Portuguese-Portugal is explicit.
   - Keep a static promotional card exported as a valid MP4 under `VID`, even when the filename contains `IMAGEM`; repeated frames do not make a decoded video an image or a technical rejection.
   - Ask visual review for one compact line per numbered asset: exact headline, product, visible language, actual human/body parts and blank/corrupt result. Enlarge the original individual image/frame when text or human presence is uncertain; do not force identical claims across a product group because filenames can describe the same product while visible headlines differ. Inspect printed photographs, phone-screen thumbnails and borders when relevant: a person or hands can be represented inside the product scene rather than posing in it. Ask the reviewer to describe those visible details without automatically excluding them because they appear in a photograph. Resolve a contact-sheet versus full-resolution disagreement from the enlarged source and persist the deciding evidence keyed to `source_drive_id`; do not let a later, smaller montage overwrite a confirmed detail.
5. Before assigning variants, reconcile each source against the existing lineage inventory and live Drive state, then list live READY filenames and calculate the next numeric variant per exact `(FORMAT, ANGLE, P_ORIENT)` group. Use three digits and preserve the real extension. If the exact group has no prior READY asset, start at `001`; an entirely empty READY folder is valid and is not a blocker.
   - Before the first write, freeze the complete per-source plan with `source_drive_id`, exact source filename, RAW/clean hashes, final filename, variant and duplicate disposition. Persist each returned destination ID and each destination/LEGACY/inventory verification separately, so an interruption exposes the precise missing layer.
   - On resume, load frozen assignments first and verify that source/clean hashes still match; do not derive new names from the now-expanded READY inventory or reclassify a completed source as its own duplicate. Seed the occupied-name set with live READY, canonical inventory and every filename already reserved in the persisted plan, including items not yet uploaded. Filter null filename values before regex parsing. Assert final filename uniqueness across distinct canonical lineages and source-ID uniqueness across all received files; allow identical final names only for explicitly reconciled exact duplicates sharing the same destination. Otherwise a pre-upload reservation can be reused accidentally after restart, or valid duplicate links can be rejected.
   - When parsing sanitizer output programmatically, invoke `verify <path> --json`; plain `verify` returns human-readable text, not JSON. Check the process result and `clean=true` before proceeding.
   - Compute the downloaded RAW SHA-256 and compare it with existing `original_checksum` and `clean_checksum` values before creating a new variant. Use perceptual fingerprints as supporting evidence, not as a substitute for an available exact checksum.
   - An equal filename is not proof of duplication: managers can export different creatives under the same Canva-style name. If the checksum/content differs, keep it as a distinct lineage and record the filename collision in notes. If the exact checksum matches an existing lineage, do not create an independent candidate or consume a new variant; attach the re-upload Drive ID to the existing lineage, validate the existing READY asset, and preserve/move the re-upload to the matching LEGACY parent.
   - User-supplied country, vertical and language define the operation when explicit; filename/folder guesses such as `UNKNOWN` do not override them.
   - Derive `ANGLE` from the dominant, persistent visible claim in the asset language. Normalize it to concise `UPPER_SNAKE_CASE` without translating it (for example, visible English `AVAILABLE LIMIT` → `AVAILABLE_LIMIT`). Keep exact amounts or longer claim text in inventory evidence/notes, not in the canonical filename.
   - For video, confirm claim and person/no-person classification across multiple frames, normally near 20%, 50% and 80%; a single thumbnail is insufficient.
   - If person/no-person evidence is incomplete or conflicting, inspect additional frames at the opening and ending and examine cropped borders before fixing `P_ORIENT`. Ask the visual reviewer to report factual visible body parts; do not inject a new rule that discounts hands/arms or conflicts with the operation’s canonical taxonomy. Human presence can appear only during the initial unpacking, outside the standard 20/50/80% sample.
6. For each item, in this order:
   - clean with the canonical sanitizer using `--agent ares`;
   - verify `clean: true` locally;
   - upload only the clean file directly to `{OP}/{IMG|VID}/01_READY`;
   - read back Drive metadata and validate ID, name, parent, `trashed=false`, size and checksum when available;
   - download the uploaded destination, compare SHA-256 with the local clean file and run sanitizer `verify` again;
   - only after those gates pass, move the original from upload to `{OP}/{IMG|VID}/99_LEGACY`, preserving its Drive ID and name;
   - read back the original and validate its new parent.
7. Append inventory entries with source/destination IDs, **exact original filename**, **exact final filename**, operation, classification, clean hash, paths, ownership/use fields and web link. The traceability pair `source_filename → destination_filename` is mandatory and must never be omitted. For an exact duplicate, update the primary lineage under the inventory lock instead of appending an independent candidate: preserve the additional `source_drive_id` and a structured link containing its exact original filename, canonical filename, RAW checksum and originating thread. An ID-only duplicate list or prose note cannot reconstruct the complete rename map reliably.
8. Final live gate: upload pending count is zero for the scoped batch, every batch destination exists in the direct READY parent, and every batch source exists in the matching LEGACY parent. Assert source-ID uniqueness, but permit several exact-duplicate sources to share one destination ID/name. Require one canonical inventory row per unique lineage plus a verified structured link for every additional source; together these must cover the entire frozen source set exactly once. Report received sources, newly created READY assets, reused existing READY assets and duplicate sources separately; inventory row count and unique destination count need not equal received-file count. Verify every expected source and destination by exact `files.get`/ID readback. A single unpaginated folder listing is not sufficient for a high-volume READY or LEGACY folder and must never turn a fully verified per-item batch into a false failure. If unrelated assets from another operation remain in the shared intake, report scoped remaining = 0 and the separate out-of-scope pending count; do not move them under the current request.
9. In the completion response, always show the rename map for every uploaded asset, in processing order:

```text
Nome original  →  Nome final em READY
```

For large batches, split the map into `IMG` and `VID`, but do not replace the per-file mapping with only a filename range. This response map is mandatory because it is the human lookup key for finding the preserved original in `99_LEGACY`.

## Running a resumable batch efficiently

1. Prefer the canonical executor and current route over copying a historical task runner. Inspect `/root/mgs-agent/scripts/ares-execute-creative-copy-clean.py` first for the existing Drive/auth/upload primitives; its historical queue CLI is not by itself the full current READY/LEGACY intake contract. Reuse validated primitives behind the current gates rather than widening the search to unrelated campaign or application trees. If a task-local adapter is necessary, inspect and parameterize its input manifest, operation, thread, expected count, classification source and output/work directories; remove obsolete embedded classification dictionaries because later assignments can silently mask stale code. Key classification by `source_drive_id` or a frozen review index mapped bijectively to that ID, never by filename alone: distinct Drive files can have identical names. Dispatch preparation, technical probing, MIME/extension and READY/LEGACY resolution per real `IMG|VID`; importing helpers from a video-only runner does not make its hardcoded format, count, dimensions or paths valid for a mixed batch.
2. Confirm that dry-run performs only reads and local preparation. Resolve existing canonical READY/LEGACY folders without `ensure_path` during dry-run; folder creation is an external write even when no media is uploaded.
3. Reuse downloaded RAW files and verified clean files across visual review, planning and execution. Validate size/hash before reuse, and keep transient media in the active profile scratch workspace; repeated downloads and sanitization waste batch time without strengthening lineage.
4. Estimate the full phase cost before launching a batch: per-item download, sanitization, upload, readback and source move accumulate even for small images. Use `terminal(background=true, notify=true)` from the outset when preparation, execution or final audit may outlast a foreground call; requesting a larger timeout does not establish the actual runtime observation limit. Consume completion in the same conversation with `process_manage(action='wait', session_id=...)`; do not introduce cron or an agent handoff for routine batch completion. If a wait is clamped or times out, keep the same process handle and wait again while it remains active; the observation boundary is not proof that the runner stopped.
5. If execution is interrupted, inspect runner liveness and the per-item state before launching anything else. Match the runner's exact command argument rather than a loose search that can match the diagnostic command itself; never start a second writer while the first remains active. Resume only missing writes from the frozen plan. If destination, LEGACY and inventory stages are all persisted as verified, bypass that item's mutation path and include it in the independent final audit by exact IDs, download/SHA and `clean=true`; re-running every completed upload/move stage wastes the execution window and can cause repeated timeouts. Keep RAW/clean files until that final audit passes.
6. Do not let generic HTTP retries replay a non-idempotent upload POST. After an uncertain result, read back persisted destination IDs or reconcile the reserved exact filename with downloaded clean SHA and metadata before adopting the target or retrying the missing upload. Filename equality alone is not sufficient evidence.
7. Paginate every READY/LEGACY listing used for variant allocation, name adoption or final reconciliation, not merely the final audit; a truncated first page can hide a collision before write.
   - When an authorized mid-execution message adds an explicitly numbered subset, stabilize and review that subset separately, then append its frozen source IDs and assignments under the batch lock after the current writer exits. Preserve every existing assignment, destination ID and verified stage; skip completed items rather than replaying their writes. Record the additional message as authority and update expected counts programmatically. An extra neighboring file not named in the extension is not automatically in scope: leave it untouched and report it separately.
8. Independently verify every source/destination ID, original/final name, parent, size/hash, `clean=true`, inventory lineage and reservation. Scope inventory assertions to the frozen batch source/destination IDs under the inventory lock: concurrent Campaign Ops can legitimately reconcile other rows, so a byte-for-byte unchanged global inventory is not an intake acceptance gate. Record observed out-of-batch changes separately without restoring them or attributing them to this batch without evidence. Re-scan intake recursively, then remove all task-local RAW, clean, readback and visual-review media only after verification passes; retain compact manifests and audit evidence.

Acceptance checks for a runner: a dry-run creates no remote folders/assets; a resumed partial batch retains the same names and destination IDs; a fully completed replay creates no new assets; pagination does not omit occupied names; uncertain uploads are reconciled before retry; final unique lineage counts match the frozen manifest.

## Failure discipline

- Stop moving a source if its clean destination has not passed every verification gate.
- On a partial rerun, detect already processed `source_drive_id` and destination IDs before creating another copy.
- Treat an empty intake or missing source IDs during a rerun as a possible completed concurrent execution, not immediately as a failed batch. Before retrying any write, reconcile every expected `source_drive_id` against `assets.jsonl`, the latest execution report, the READY destination IDs and the LEGACY parents. If all sources are complete, switch to verification/reporting; if only some are complete, resume only the missing IDs.
- Serialize batch writes with an operation/batch-scoped lock when parallel Discord sessions can receive the same continuation message. The lock complements, but never replaces, live source-ID and inventory reconciliation.
- Preserve the originating request thread as `thread_id`. A separate thread that only supplies authorization, permission context or a continuation message must be recorded separately (for example, `authorization_thread_id` or notes) and must not overwrite the asset lineage thread.
- Keep status in folders/inventory, never in filenames.
- Do not create placement/language subfolders under READY.
- Report consolidated counts and READY links; do not attach the batch unless explicitly requested.

# PHP security advisory: runtime audit before intervention

1. Read the supplied image/email and extract the actual CVEs, fixed versions, date and provider scope. Verify technical claims against php.net and the linked php-src advisories. Separate active attack attempts, demonstrated exploitation and evidence of compromise of the specific company; one does not prove the others.
2. Read the provider's current advisory. Managed/shared hosting remediation does not establish that a self-managed VPS is patched. A provider promise of automatic rollout does not establish installation on a named host.
3. Audit each host independently. For RunCloud, derive the active service from live app/runtime state, resolve the FPM MainPID and /proc/<pid>/exe, read the matching FPM binary version, installed package revision and source repository. Installed legacy binaries do not establish active legacy HTTP workloads. Cached webapp inventories are discovery hints, never current counts or migration proof.
**Unix-socket collision gate.** Before any PHP-FPM restart, canonicalize every pool listen path with realpath and compare it against all listening Unix sockets and systemd socket units, including non-PHP applications. `/var/run/name.sock` and `/run/name.sock` can be the same filesystem endpoint. A stale provider-created PHP pool can overwrite a live Node/systemd socket during restart while both processes remain active. Detect and freeze this conflict before mutation; do not restart through it. If it is discovered after an authorized restart, retain the patch, diagnose the actual socket owners and request the exact additional system-config/service confirmation rather than blindly downgrading PHP or restarting unrelated services.
**Confirmed socket-collision recovery.** For an explicitly confirmed socket-collision repair, move the PHP pool listener and its matching Nginx FastCGI fallback together, preserving the Node/systemd socket path. Back up and fingerprint both exact files, test both configurations before service actions, stop the application service and its socket together, restart FPM on its isolated path, then start the application socket/service and reload Nginx. Verify live socket ownership, public HTTP and browser navigation, direct-origin access denial, and unchanged database-service PIDs; active services alone do not prove a working HTTP listener. Revalidate the separation after provider config regeneration; a local file repair does not prove that a future control-plane rebuild will preserve it.
4. Do not use php -v alone as HTTP-runtime proof. Use the exact php-fpm -i and sanitized php-fpm -tt output for baseline and pool-level settings; retain only relevant lines in the report because a full config dump may include secrets. A CLI/default INI value cannot prove the effective configuration of every running web pool. Record any gap honestly.
5. Check distributor backports by exact package revision and CVE/USN/changelog rather than comparing only upstream PHP_VERSION. Ubuntu may retain an older upstream number while shipping the complete security fix.
6. Refresh APT indexes before concluding that no patched candidate exists. Capture installed/candidate revisions and a simulation for only the intended PHP packages. Do not run a blanket apt upgrade, switch repositories or compile PHP merely because a notice recommends generic commands.
7. If RunCloud API returns 429, retain safe rate-limit headers and honor Retry-After. When the declared wait exceeds the task window, stop API retries and use the existing authorized SSH route for guest diagnostics; do not hammer, rotate credentials or fabricate a full API inventory. Preserve the resulting inventory limitation.
8. Treat temporary settings and WAF rules as defense in depth, not proof of remediation. Check provider-announced mitigations on the actual FPM configuration before crediting them; describe an unconfirmed rollout without inventing a cause. Never disable all multipart traffic indiscriminately on WordPress, where uploads, updates and forms may depend on it.
9. Freeze the exact package transaction and host scope before Critical Subset confirmation. Prefer a security patch within the existing supported branch over an unnecessary major/minor migration. Back up first, preserve provider-managed configuration, restart/replace every old PHP worker and validate public/origin application canaries after authorized mutation.
10. Close research separately from remediation. State which hosts were inspected, which remain unverified, the confirmed risk and exact decision needed. Do not claim an exploit scan or clean bill of health when only versions/configuration were audited.

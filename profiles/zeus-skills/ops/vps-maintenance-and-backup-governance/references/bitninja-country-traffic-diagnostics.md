# BitNinja country/traffic diagnostics

Use for read-only requests asking whether BitNinja blocks legitimate traffic from a country.

1. Validate operator/channel authority and the exact corporate domain scope before reading or disclosing per-host traffic. Union the applicable positive corporate registries when appropriate; a hosting account is not an ownership registry. Never attribute shared-server incidents to corporate sites without a matching hostname.
2. Discover each server independently: installed package, active BitNinja unit, CLI help, Nginx domain-to-webapp binding, access logs and WAF/Captcha logs. An inactive/uninstalled BitNinja on one host cannot explain its traffic failures; do not enable it as incidental recovery.
3. Freeze one absolute UTC window. Scan original access logs and applicable rotations, preserving file coverage, timestamp range, parse failures and per-host results. Nginx buffered writes can appear after an earlier scan despite timestamps within the same frozen window.
4. Check geolocation database **build metadata**, not file mtime. Legacy GeoIP.dat can have a recent filesystem timestamp but a years-old build. Prefer the current GeoLite2-Country.mmdb; if Python bindings are absent, use an isolated scratch dependency or a pure-Python reader injected in process memory, never install into the production agent or remote system merely for this audit. Label geographic inference as approximate.
5. Separate requests, unique IPs, page visits and active paid campaigns. Log requests from a country do not establish active acquisition targeting. Count programmatically and exclude duplicate retired installations when reporting unique hosts.
6. Inspect current firewall/ipset state in read-only mode. Distinguish blacklist DROP, greylist/challenge and country-wide rules. Check exact IPs and CIDR membership; current list membership is not proof of the action applied to a historical request.
7. Correlate CaptchaHttp records only with proven hostname/request evidence. IP-only shared-server totals, matching themes, or similar slugs cannot identify the destination site. Distinguish challenge displayed, malformed captcha request, solved captcha and confirmed origin delivery.
8. HTTP 403/503 alone does not identify BitNinja as the cause. Separate article/quiz paths from xmlrpc/plugin/theme probes, and label bot/attack classification as a hypothesis unless corroborated. A public 200 from the auditor's VPS is not a South African end-to-end probe and cannot rule out IP-specific blocking.
9. Report the verified host coverage, window, current protection state, confirmed per-IP restrictions, legitimate-flow samples and residual hostname/retention/egress gaps. Do not claim all portfolio sites or zero false positives when external hosts or country-local testing remain unverified. Firewall/BitNinja allowlist changes retain the exact Critical Subset gate; never whitelist an entire country or disable protection as an audit shortcut.

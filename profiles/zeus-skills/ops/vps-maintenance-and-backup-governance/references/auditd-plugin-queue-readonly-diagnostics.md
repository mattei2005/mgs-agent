# Auditd plugin queue: read-only diagnosis

Use when auditd reports `queue to plugins is full - dropping event`, including BitNinja AuditManager forwarding.

1. Separate three predicates: kernel backlog/loss from `auditctl -s`; local audit-file writing/suspension; and the dispatcher/plugin queue. Kernel `lost=0` does not prove zero plugin-forwarding drops. A running plugin process does not prove that its input queue is draining.
2. Read only allowlisted settings from auditd.conf (`q_depth`, `overflow_action`) and plugin metadata (`active`, `path`, `type`, `format`), not arguments or raw event payloads that may contain sensitive command information. Identify the actual enabled plugin and confirm its process/service state.
3. Obtain the daemon's internal state using the locally documented interface. Audit3.0.7 does not support `auditctl --signal state`. Read the installed auditd(8) manual first; where it documents SIGCONT, send SIGCONT to the exact auditd PID to request `/var/run/auditd.state` (normally `/run/auditd.state`). This requests a diagnostic dump, not a restart or config reload. Do not repeatedly invoke an unsupported CLI option or install newer audit packages just to inspect state.
4. Capture at least two bounded samples of current plugin queue depth, queueing suspension, active-plugin count, local logging status and kernel backlog/lost. A current depth of zero with active dispatch, unsuspended logging and kernel backlog/lost zero demonstrates that the observed pipeline is presently drained; it does not recreate already dropped plugin events or prove zero future loss.
5. Preserve sticky historical fields such as `max plugin queue depth used` and `plugin queue overflow detected`. The `reporting limit reached` message can suppress subsequent overflow notifications, so silence in journal alone is not a recovery predicate. Do not infer total dropped events from the handful of printed warnings.
6. Report the proven immediate failure mode (the configured queue filled) separately from the unproven cause of the burst or consumer slowdown. Do not attribute it to a reboot, attack, PHP request or maintenance probe merely because timings overlap.
7. Do not silently change audit rules, disable the security plugin, reset counters to hide evidence or blindly enlarge the queue. A persistent overflow needs workload/consumer measurements, an exact config/version manifest, a scoped backup, Critical Subset confirmation where system files are affected, and post-change queue/forwarding validation. A drained transient can be disclosed as historical forwarding loss without calling the whole server or every website unhealthy.

## Executable-permission failures and missing registration

- Before repairing a rejected plugin executable, freeze its regular-file identity, owner/group, content checksum and mode against a validated backup, then verify that the active auditd `plugin_dir` still contains the expected registration. A permission repair cannot reactivate a plugin whose `.conf` is now absent.
- Treat `Number of active plugins = 0` plus queue depth zero as **no active forwarding**, not a recovered/drained pipeline. Prove local log writing with a harmless tagged audit canary separately from plugin activation and downstream delivery.
- If registration disappeared, reconcile audit → inventory → REPORT-INFRA → Git → sessions before attribution, then inspect bounded vendor lifecycle logs and filesystem timestamps. A failed vendor startup and matching directory timestamp support correlation, not proof of who removed the file. Preserve `unattributed concurrent change` when evidence is incomplete; never invent an operator action or call it an intrusion.
- Restore a missing `/etc/audit/plugins.d` registration only through its own applicable Critical Subset gate. Prefer the exact pre-maintenance archived bytes, UID/GID and mode, validate the restore candidate hash, and preserve audit rules, credentials and unrelated modules. Do not synthesize a new registration or use a broad vendor-module restart to bypass the missing-config write gate.
- Use the installed auditd manual to choose reconfiguration. When SIGHUP is documented but systemd exposes no `ExecReload`, signal the frozen live auditd PID directly and prove its PID and protected application PIDs remain unchanged. Validate plugin process/active count and two queue/logging samples afterward; absence of new errors alone is not recovery.
- Record that vendor package replacement can reset an executable-mode repair. Do not add a chmod cron, post-install hook or persistent permission override as an incidental recurrence fix without the separate authorization it requires.

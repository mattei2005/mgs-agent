# Maintenance preflight integrity boundaries

Use this note when the final pre-reboot gate mixes exact package versions, tool-mediated command output, rollback manifests, and a detached validator.

## Exact version comparisons

- Compare `dpkg-query` output to frozen expected versions **inside one host-side process**. Emit only aggregate booleans/counts and safe package names after the comparison.
- Do not compare values after they have crossed a tool-output or chat-rendering boundary: credential/redaction filters may mask numeric substrings, making distinct underlying strings render identically or making a correct value compare against a masked copy.
- Pass `-f=${Version}` as a literal argv element. In shell, quote it as `-f='${Version}'`; unquoted `${Version}` is expanded by the shell before `dpkg-query` runs and can falsely classify every package as divergent.
- Prefer a saved preflight script plus direct execution when quoting, redaction, or nested tool wrappers would otherwise influence the evidence. The script must exit nonzero on any failed gate and print one compact JSON summary.

## Multi-host status collection and safe recovery

1. Recover each target's established transport from the prior successful collector: host, user, port and trusted host-key store. Keep credential values in the approved secret transport and out of stdout, argv and saved reports.
2. Freeze one timestamped JSON observation per host with separate predicates for metadata refresh, `apt-get -s upgrade`, `apt-get -s dist-upgrade`, running kernel, reboot marker, failed units and restart diagnostics. Preserve each command's exit status; an empty transaction is meaningful only after a successful refresh and simulation.
3. Run independent hosts concurrently, but persist completed host results before aggregation. Catch errors at the individual predicate boundary and still emit the completed host fields; a late optional diagnostic must not erase an earlier successful package audit.
4. Discover optional diagnostic availability before invocation. Record unavailable checks explicitly without installing tools as part of an informational status request; do not equate unavailable restart diagnostics with zero pending restarts. Use the existing completion contract to decide whether that gap blocks the requested claim.
5. If SSH rejects a host key, first reconcile the exact host/port and the established `UserKnownHostsFile` from the prior approved route. Retry with that existing trusted store and `StrictHostKeyChecking=yes` when it resolves the mismatch. Never use `StrictHostKeyChecking=no`, accept a replacement key, or create new trust merely to finish the audit; unexplained fingerprint drift remains a blocker.
6. Retry only the missing or invalid host/predicate, merge its replacement into the saved results by stable target identity, and derive verified-host totals from the aggregate. Keep failed-attempt evidence separate from the final observation so recovered transport errors do not become fictitious infrastructure pendencies.

## Snap update availability, timing and completion

1. Discover Snap availability without installing it. Where present, collect `snap list`, `snap refresh --list` and command exit statuses alongside the APT audit. For a candidate, use `snap list --all <name>` to distinguish the active revision from retained disabled revisions; version labels alone do not identify the installed revision.
2. Read `snap refresh --time` for the native timer, last run and next estimated attempt. To answer who set the time, inspect `snap get system refresh.timer` and, when relevant, `snap get system refresh.schedule`. A missing option means no explicit value for that option, not a failed refresh; distinguish the effective native schedule from a custom setting. Never claim to have scheduled an update merely because its native next-run estimate was read.
3. Attribute practical impact before recommending a manual refresh. Read `/snap/<consumer>/current/meta/snap.yaml` for `base:` and inspect `snap services <consumer>`; a base update can affect an application using that base even when MGS gateways run outside Snap. State expected impact, not a guarantee of zero interruption or reboot requirement inferred solely from the word `base`.
4. When the owner elects to wait, schedule observation after the native estimate through the existing scheduling policy. Keep the updater untouched. Give the observer the exact target/channel, active and candidate revisions, dependent services, success predicates, delivery destination and an explicit no-force/no-restart scope. A one-shot observer is not an automatic continuation: if the updater defers, persist its actual next estimate and create at most one bounded successor rather than silently abandoning the notice or leaving overlapping observers.
5. At observation time, combine the active revision, `snap refresh --list`, `snap changes` and `snap change <id>` when an applicable change exists. No rows in `snap changes` alone do not prove either failure or completion; reconcile with active state and other receipts. If a candidate remains listed after an automatic attempt, inspect a bounded `journalctl -u snapd --since '<attempt-window-start>' --no-pager -n 40` window. Record an automatic attempt reporting no eligible update separately from a later listing offering a candidate; that discrepancy does not establish a failed installation or prove a particular store rollout/eligibility cause. Keep the cause unproven unless supported by additional evidence. Validate affected services and the scoped MGS gateways independently before reporting success. For a Livepatch consumer, reduce `canonical-livepatch status --format json` to kernel/support/patch state before returning tool output and omit machine/subscription identity.
6. Before promising or creating a successor from a one-shot observer, check the execution surface's scheduling authority. Hermes cron runs prohibit recursive cron creation; do not bypass that boundary through CLI, Python imports, direct scheduler JSON writes or an alternate scheduler. If no successor was pre-provisioned, preserve the native update schedule, record the observation/checkpoint and report the missing follow-up executor as a real orchestration blocker; a native next-refresh estimate is not a scheduled Zeus verification. When an authorized foreground conversation later resumes the same request, read the original job's enabled/state/repeat/next-run and delivery receipt before creating anything. If the job was consumed and no live successor exists, use the native scheduler to provision exactly one bounded read-only successor under the existing notification authorization. Apply the global pre/post collision audit, backup and exact-job readback from `log-monitor-discord-alert`; do not reset the consumed job's history, create overlapping observers, or broaden the production scope. Record the repaired executor separately from update completion.
7. Deliver one verified completion or a precise real blocker in the origin conversation. Keep the checkpoint pending while a successor is scheduled; do not call scheduling success an update success. Do not turn a later revision of another package into implicit permission to broaden the update.

## Security parity beyond the package graph

1. Treat zero APT/Snap candidates as repository currency, not proof that every daemon and bundled dependency has the vendor's security fixes. Inspect live executable versions for provider Nginx/PHP, WAF-embedded Nginx/Node and automation-driver Node; compare official fixed branches and exact distributor revisions/changelogs. Missing backport evidence remains unverified, not a confirmed exploit or a clean bill of health. Do not replace a provider-managed binary or switch repositories incidentally.
2. For an all-server request, union the current provider inventory with canonical per-domain host bindings and credential metadata, including non-RunCloud/AWS hosts. A successful SFTP read certifies only the accessed files; it cannot certify OS/APT/kernel/PHP service health. Keep external hosting with unknown underlying VPS identity and inaccessible historical hosts as explicit coverage gaps; never reduce the denominator silently.
3. When using `ss --mptcp`, retain only rows whose first Netid field is exactly `mptcp`: the command can also print ordinary TCP rows. Attribute listener PIDs/executables and distinguish wildcard binding from externally verified reachability. Changing sysctl, firewall or a WAF listener still requires its exact authorization gate.
4. For WordPress security applicability, compare each branch with the official security release/backport or update API, not merely with the newest major/minor number. Read files and current webserver bindings without bootstrapping WordPress for inventory-only checks; an old-looking directory can still be configured as a webapp, and a backup-like name does not prove isolation.

## Dual-manifest pattern

A maintenance set contains both immutable execution inputs and mutable evidence. Do not use one checksum file for both purposes.

1. Build an immutable reboot snapshot containing the validator, finalizer, unit template, frozen package targets/pre-state, exact active launcher/runtime files, gateway configs, and the helpers invoked by the finalizer.
2. Exclude logs, results, audit, inventory, checkpoints, transport receipts, and generated bytecode from that immutable snapshot; these are expected to change during closure.
3. Make the detached finalizer and post-boot validator check the immutable snapshot before mutation.
4. Separately regenerate a complete backup manifest at the final pre-reboot boundary and reverse-check it once as recovery evidence.
5. If any immutable source changes after hashing—even a preflight fix—regenerate the immutable snapshot, regenerate the complete manifest, rerun syntax/compile/unit verification, and only then schedule reboot.

This prevents two opposite failures: a stale whole-backup manifest blocking a valid reboot because logs changed, and a too-narrow snapshot allowing validator/finalizer drift after approval.

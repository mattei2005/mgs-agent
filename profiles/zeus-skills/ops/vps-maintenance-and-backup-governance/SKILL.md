# VPS Maintenance and Backup Governance

## Purpose

Produce a grounded maintenance decision for the MGS VPS without confusing package-index refreshes, untagged Git development, local customization drift, backup integrity, backup redundancy, or cleanup-policy eligibility. This skill governs the **audit and decision boundary**; actual Hermes deployment/restart still follows `hermes-agent-operations`, and monitor implementation still follows `log-monitor-discord-alert`.

## Standing completion contract for Rodolfo

- When one request names more than one VPS, domain, site, or runtime, create a separate target/phase ledger before mutation. Prove each workload-to-host binding from the live control plane plus domain/webapp readback, keep backups, authorization gates, results, and rollback evidence scoped to that host, and never transfer a successful audit or authorization from one VPS to another merely because both appeared in the same conversation.
- Interpret `atualizar tudo`, `nenhum commit pendente`, or invoking the standing controlled VPS + Hermes plan without an explicit stable-only limit as a request to port Hermes through the latest fetched `origin/main`, even without a newer stable tag; require zero known upstream commits at the validated cutover. Stable-only must be explicitly requested by Rodolfo—never infer it merely because the status discussion began with the newest public release.
- Before requesting an exact-SHA Critical confirmation against a moving `origin/main`, run a bounded stability observation and require several consecutive identical fetches. If the ref changes on nearly every observation, stop once and ask for a cutoff policy—either wait for a quiet window or explicitly freeze the newest SHA and classify later commits as the next update—instead of trapping Rodolfo in repeated per-SHA confirmations that cannot converge.
- Bind every moving-main confirmation to the frozen SHA or the explicitly approved cutoff policy. A candidate validated for an older SHA remains inactive evidence; when the new delta has no overlap, rebase it and rerun the focused and full gates rather than rebuilding the whole port, but never activate it by implication.
- When Rodolfo says to keep only the latest backup, define the named recovery class and retain its newest validated recovery set before freezing older backups for deletion. A recovery set may combine a control-plane archive with native profile/database snapshots. Do not infer permission to retire source checkouts or launchers from backup-only language; if runtime cleanup is also requested, apply the runtime dependency gates separately. Unrelated system, site, browser-session, credential and offsite recovery classes remain outside scope unless named.
- Do not close an expressly requested cleanup by relabeling older in-scope backups as optional or intentionally retained. Keep the exact deletion gate visible until executed or changed by Rodolfo; distinguish any technically required active-code dependency or unproven replacement as an explicit blocker, not a discretionary retention choice.
- For cleanup authorized only if the dashboard loses no data, prove the live application/database host and classify local test state, raw report copies, pre-import dumps and persisted production records separately. Preserve production facts and compact provenance; disclose irreversible loss of historical test/recovery state without calling it redundant. Follow the scoped workflow in `references/backup-retention-scope-and-redundancy.md`.
- Keep one-time disposal and future producer retention as separate outcomes. Approval to remove existing material does not silently authorize a new deletion cron, changed backup cadence or disabled import automation; report any remaining accumulation risk honestly.
- For an old-backup review, split historical profile/database snapshots, compact recovery evidence and reproducible code/test copies before presenting a cleanup amount. A validated newer recovery set does not prove historical-state subsumption. Route snapshot comparison before opening SQLite files; preserve unproven state and propose only the independently validated exact lot. Report the original occupied amount and the smaller proven reclaim as different quantities, not as if the whole backup class had become disposable.
- When Rodolfo challenges high disk usage after cleanup, distinguish completion of the approved lot from necessity of the remaining data. Reopen read-only classification of the largest current producers instead of merely repeating successful deletion checks. Describe unclassified or reconstruction-unproven material as preserved pending evidence, not operationally indispensable; neither preservation nor a housekeeping no-op proves that no more space can be reclaimed. Explain the largest findings as numbered problem/cause/solution items and keep duplicate potential, fully gated reclaim and observed savings separate.
- For long authorized maintenance, suppress stage narration. Message Rodolfo only at full validated completion or at the exact Critical Subset/decision blocker. If he explicitly requests notification when one phase finishes, treat that phase as a delivery milestone: notify once after its own acceptance gates pass, distinguish the remaining authorized phases, and do not postpone that notice until the entire initiative ends. An installed package batch or dispatched reboot is not a completed VPS milestone.
- For version/commit questions, answer installed release/base, latest official stable, pending stable commits and pending main commits directly; do not force a maintenance completion template onto an informational review. For benefits questions, explain what changed, practical MGS impact and any adoption requirement in numbered topics. Label reviewed-but-not-installed benefits as prospective, and separate core fixes from opt-in plugins and Desktop-only features.
- Explain maintenance residuals in plain PT-BR: distinguish updates currently released to this host, newer versions deferred by Ubuntu's staged rollout, and an unavailable external information feed. Say that all host-eligible updates were installed rather than implying every version in the catalogue was installed. When Rodolfo asks about numbered points, answer each in order with what it means, its practical impact and whether any action remains.
- For detached maintenance, state the current execution state and its owner explicitly: `já concluído e validado`, `agendado para executar automaticamente`, or `bloqueado aguardando decisão`. Never leave `falta reiniciar` alone when an executor is already responsible for that restart; ambiguous future-versus-completed language makes Rodolfo ask whether he still needs to act. Reconcile the live receipt before answering a follow-up.
- When Rodolfo chooses to await a native automatic update and requests notification, preserve the native schedule and create only a read-only follow-up. Label the updater's next-run time as an estimate and distinguish it from Zeus's verification time. Verify the follow-up's persisted schedule/delivery and its bounded continuation or blocker-delivery path before promising the notice; a consumed one-shot does not preserve monitoring. On a later status request, reconcile both the update and the observer lifecycle. If the observer ended without a successor, repair the agent-owned follow-up from an authorized foreground surface under the existing notification scope, verify the exact new job, and acknowledge the monitoring gap separately from the still-pending update. Do not force the update, change its timer, or ask Rodolfo to repair the scheduler.
- Classify a failed check's applicability before making it a completion blocker. Preserve the failed observation and investigate its scope; a proven non-applicable optional dependency is a disclosed residual, not a successful check or missing VPS update. Keep unknown applicability blocking and use the routed validator reference for device/service-specific predicates. Make multi-host collectors preserve independently completed predicates even when a later diagnostic fails; report that diagnostic as unavailable rather than discarding the host's valid package/kernel observations or silently treating the missing check as healthy. Use `references/maintenance-preflight-integrity-boundaries.md` for partial-result and SSH-trust recovery.
- When Rodolfo takes over a provider restore or says to stop, stop all competing probes and mutations immediately, verify whether any background executor remains, and report that exact state. Treat the owner restore as an authorized concurrent control-plane action; resume only after its completion is read back, never while the provider is replacing the webapp/database.
- Before recommending a provider snapshot for restore, compare its absolute timestamp and displayed timezone with the last validated release—not with the timestamp of a Discord message or a relative-age label. Corroborate the match with expected artifact deltas such as webapp/database size changes, but label that as supporting evidence rather than identity proof; state explicitly what later changes the restore will discard.
- Treat provider `Completed` plus matching versions/sizes as restore transport evidence, not application recovery. After the owner restores, require exact release markers **and the user-visible canary that motivated recovery** at public, cache-busted, origin, and rendered-browser layers. If the expected state returns but the defect persists, classify that snapshot as faithfully restored but unsuitable and repair the component; never repeat the same restore merely because its timestamp looked correct.
- When Rodolfo asks what he needs to provide after a technical blocker, answer `nada` immediately if the blocker is agent-owned, fix it and continue under the existing authorization. Never turn a self-resolvable probe, helper or validation failure into a user dependency; interrupt only for an exact Critical Subset confirmation or a decision/credential/cost gap that cannot be recovered with the approved routes.
- When Rodolfo says he already answered both questions, reconcile each question with its corresponding reply and completed effects before asking again; repeated short approvals do not create a new gate for the same unchanged scope. Continue the authorized review, but do not reinterpret its approval as permission to delete an undisclosed batch. Treat a plain `sim` immediately following an exact destructive-manifest confirmation as the final approval for that lot: bind its message to the shown manifest and executor checksums, rerun the frozen preflight, and execute without a third confirmation when it passes. Elapsed time alone does not invalidate approval; actual scope, fingerprint or verifier drift does.
- For a bounded review whose approved outcome is preservation when disposal cannot be proven, classify every target and close the review with explicit protected reasons if no eligible batch exists. Say `revisão concluída; nada apagado; nenhuma confirmação pendente`, distinguish occupied bytes from eligible reclaim and observed savings, and keep the preserved targets out of pending-deletion language. Do not use this review-only closure to cancel a separately requested deletion or retention override.

## Audit workflow

1. **Recover the real pendency.** For a follow-up status question, select the exact checkpoint and inventory records by request/thread ID before expanding discovery; filter individual records, not an enclosing JSON object whose descendants contain the search term, because that can dump the entire registry and hide the relevant result. Project only state, next step, timestamp and evidence paths; open the pointed phase receipts next. Use current runtime first; use checkpoints/audit/inventory and prior sessions only to explain what was pending. A historical package list never overrides the current APT graph, running kernel, or live service state. A scheduled or detached update is still pending until the finalizer log/result, canonical launcher, target service start times, and required report/readback agree; reconcile those sources before repeating any earlier success claim.
   - When the audit itself runs inside Hermes, never use bare `command -v hermes`, `hermes --version`, or the auditor process environment to identify the production runtime: the active session may prepend an install-store or staged environment to `PATH` and export runtime hints from a different executable. Resolve each gateway through `systemctl show <agent>-gateway.service -p MainPID -p ExecStart`, inspect `/proc/<MainPID>/cmdline` and `/proc/<MainPID>/exe`, then reconcile those paths with `readlink -f /root/.local/bin/hermes`, the activation receipt, and the runtime Git SHA. Invoke version/update/doctor probes by the reconciled absolute launcher path; treat any environment-derived “active venv” line as advisory until it agrees with the running PID evidence.
   - Treat a green monitor as evidence only for the predicate it implements, not for the producer it watches. For Git auto-versioning, verify the watcher unit's `ActiveState`/`UnitFileState`, the audit reason for any intentional containment, working-tree cardinality, and `HEAD == origin/main`; a no-alert auto-push monitor can remain green while the auto-commit producer is deliberately disabled and local changes accumulate. Before declaring an authorized maintenance change synchronized, verify each scoped artifact against its `origin/main:<path>` blob and read back the exact inventory record from that remote revision; equal local/remote HEADs can still coexist with an untracked receipt or an uncommitted closure record. If the watcher is healthy and merely batching, wait within its configured maximum window, then fetch and repeat the scoped checks without substituting a manual commit or changing batching.
2. **Freeze a coherent observation.** Refresh package metadata and Git refs when allowed, then capture timestamp, running kernel, reboot marker, update candidates, Git SHAs/tag, services, disk, and backup roots. Do not calculate against refs while a fetch is still changing them. On RunCloud webapps, derive the active PHP service from the live `phpVersion` readback (for example, `php83rc` → `php83rc-fpm`) and pass it into collectors; never hardcode a legacy PHP unit, because that produces a false inactive-service finding after a runtime migration.
   - Reduce preflight evidence before returning tool output: select inventory records by exact ID and project only the fields needed for the active phase; parse Ubuntu Pro/Livepatch JSON into health and update counts instead of printing account or contract metadata. Filter APT simulations to transaction summaries and `Inst`/`Remv` rows while checking exit codes independently; autoremove suggestions and historical inventory bodies obscure the confirmed transaction and inflate context. Use `references/controlled-package-and-node-tooling-update.md` for the bounded collection recipe.
3. **Separate update classes.** Report standard OS/security updates, third-party repositories, inaccessible subscription/ESM fixes, language/package-manager updates, Snaps, and Git application updates independently. For a general VPS update-pendency question, check installed Snap packages with `snap refresh --list` as well as APT before concluding that no updates remain; a zero APT transaction proves only APT currency. If coverage is intentionally narrower, name that boundary in the initial answer. Use `references/maintenance-preflight-integrity-boundaries.md` for native Snap timing, dependency and completion checks. Treat provider/control-plane flags such as `securityUpdate=true` only as a prompt to inspect the live package graph, never as classification proof: after refreshing indexes, record the exact installed/candidate versions, repository pocket, source changelog, and matching USN/OVAL evidence. A package with a security-related name or purpose can still be a normal `*-updates` bugfix; do not call it a security update without advisory evidence.
4. **Distinguish stable release from moving main.** Name the latest public tag, installed checkout, and current upstream SHA. Count pending commits from the installed checkout and untagged commits since the tag separately.
5. **Measure customization risk.** Resolve the verified upstream base and inventory manifest-backed patches, committed `base..HEAD` paths, staged/unstaged changes and untracked files. A clean working tree does not mean stock code. Union that complete surface, intersect with upstream-changed paths, and run reverse/clean-target forward checks. Textual overlap is not an actual conflict; a failed apply check names the real port blockers.
6. **Inventory backup storage by operational set.** Count bytes/files/dates/errors at first-level backup sets and separately include update reports, staging/workdirs, hidden secure roots, system-managed backups, and protected archives. Label every count by its actual unit: archive file, operational set, directory entry or provider recovery point; hundreds of backup-like entries are not hundreds of complete VPS snapshots. Separate on-host occupancy from off-host recovery inventory, because deleting an off-host backup cannot free the VPS filesystem. For Hermes, enumerate every sibling `hermes-agent*` checkout and every `hermes*` launcher symlink in the same fresh pass; derive the active runtime and immediate rollback from the live launcher plus the latest validated activation receipt instead of assuming the previous cleanup manifest covered them. Before proposing any runtime deletion, map the live profile/session roots separately and state whether they intersect the target set: a runtime is application code and a launcher is an executable pointer, not Discord thread or conversation storage. Historical receipts may link a runtime to the thread that created it, but that provenance does not make the thread data part of the runtime tree.
7. **Audit the cleanup implementation and recurrence, not just its cron.** Read its scan roots, filename patterns, keep-latest logic, producer cleanup/finally paths, and retention. A green dry-run proves only the policy it implements; it does not prove that legacy names, application-private evidence, test databases, or staging trees are covered. For a high-disk alert, capture live block and inode usage first, traverse the same filesystem from `/` into only the largest roots with mount-bounded `du`, and reconcile the last validated post-cleanup `df` baseline. If the same operational set consumed the recovered space again, classify the cause as a producer/retention recurrence rather than another one-time residue cleanup. Within application evidence roots, measure live state, `candidate`/`stage` trees, database dumps, restore archives, JSON/browser evidence, and UUID test databases separately. Trace the producing code before assigning the cause: `candidate/private` may contain newly generated isolated test state rather than a recursive copy. Describe recursive recopy only when the producer or content comparison proves it; otherwise report generated test residue or unclassified evidence accurately. Check process `cwd`/`exe`/`fd` references before calling any candidate stale, and never let an active candidate disappear inside a broad directory-level reclaim estimate. A cleanup without producer-retention closure is temporary relief, not recurrence prevention.
8. **Classify before proposing deletion.** Use exactly three classes: eligible under current policy; eligible only after an explicit retention/policy change; protected or containing unique data. Never blend them into one reclaim number. For completed test/staging copies, start any review-age window from proven, validated task closure—not directory mtime. Missing closure, dependency or retained-recovery evidence means preserve the target; elapsed time opens review, not automatic deletion eligibility. Separate acceptance of a review model from approval of an exact deletion batch, and explain that distinction in plain language rather than asking Rodolfo to judge technical metadata.
9. **Validate retained recovery paths.** Before naming an archive deletable, validate the archives that remain and prove that a supposedly redundant snapshot has no unique state required by the canonical archive.
10. **Quantify the decision without hardlink inflation.** Report both the naive allocated sum and an inode-aware reclaim estimate that credits file blocks only when every hardlink is inside the target set. Use separate `du -x -B1 --max-depth=1 <root>` runs for discovery only; never add their independent totals, because each invocation may count the same cross-root hardlinks again. Build the final category ledger in one filesystem-bounded traversal using `lstat`, `st_blocks * 512` and `(st_dev, st_ino)` deduplication, without following symlinks. When an inode occurs in different categories, remove its first category assignment and credit it once to a shared-hardlinks bucket; allocation to the first encountered pathname makes category totals traversal-order dependent. Keep overlapping review roots non-additive. Reconcile the ledger sum against a fresh `df -B1`, disclose scan errors and material residuals, and distinguish allocated occupancy from reclaim: blocks are releasable only when every hardlink is inside the approved target set and no open reference keeps them allocated. After any authorized cleanup, verify path absence and treat the measured `df` free-space delta as the authoritative observed result.
11. **Cover every persistent filesystem explicitly.** Scan `/`, `/boot`, and `/boot/efi` separately whenever they are different devices; prune pseudo-filesystems and mount crossings, record errors per filesystem, and never infer whole-VPS coverage from the root filesystem alone.
12. **Report conclusion first.** State whether reboot is required, what can update routinely, what requires a controlled window, exact high-confidence cleanup candidates, protected classes, and the residual governance gap.
13. **Re-freeze the package graph immediately before “100% updated.”** Refresh APT metadata and rerun both upgrade simulations after application activation and final smokes. Packages published after an earlier green gate are a new Critical Subset scope: keep the already validated Hermes phase closed, name the new package/version transaction exactly, and interrupt Rodolfo only for that decision instead of silently extending the prior confirmation.

## Multi-phase maintenance closure ledger

When one request combines VPS maintenance, reboot, Hermes/application update, and backup or unused-file cleanup, treat each as an independent acceptance phase even if they share one thread:

1. Create one checkpoint/checklist entry per requested phase at intake: package maintenance, reboot validation, application activation, cleanup inventory, destructive confirmation/execution, and governance closure as applicable.
2. Mark the overall request complete only when every requested phase is either `completed_validated` or explicitly deferred/cancelled by Rodolfo. A green VPS or Hermes update never implies that cleanup also ran.
3. If cleanup must wait for successful activation or Critical Subset confirmation, keep it visibly pending with the exact next gate. Do not bury it in a generic residual or close the parent task from the currently active foreground subset.
4. After activation, run a fresh inventory that includes artifacts created by the update itself—candidate runtime trees, verify checkouts, full profile archives, prechecks, and rollback sets—before freezing the cleanup manifest. Pre-update size estimates are not the post-update target set.
5. On interruption, gateway recovery, handoff, or work continued in another thread, reconcile the original request and phase ledger before the final answer. State separately: `VPS updated`, `Hermes updated`, and `cleanup executed/not executed`.
6. A status answer must use live readback plus the ledger. If no destructive audit boundary and absent-target validation exist, say plainly that cleanup was not executed, even when candidates were identified and the disk is healthy.
7. For a long maintenance run already authorized by Rodolfo, do not narrate each internal stage. Execute through all non-blocked phases and deliver the requested completion milestones under the standing completion contract above. Outside those explicit milestones, interrupt only when Critical Subset scope drift or another decision blocker requires Rodolfo; visible tool progress is not a substitute for, or a reason to add, stage-by-stage messages.

### Cleanup-candidate continuity and owner closure

Avoid making a phased cleanup sound like an endless stream of newly discovered deletion targets:

1. Keep a stable cumulative ledger for every candidate and label its origin as **pre-existing residue**, **artifact created by the current analysis**, or **the same target re-fingerprinted after drift**. Never count analysis-created temporary storage as pre-existing reclaimable space.
2. When a volatile target changes and requires a new manifest hash, state explicitly that it is the **same scope with a refreshed fingerprint**, not a new cleanup finding. Show the prior candidate identity and keep cumulative bytes non-additive.
3. Before asking another Critical Subset confirmation, explain in one sentence whether the target is genuinely new, newly classified from an already-disclosed residual, or unchanged except for metadata/hash drift.
4. Treat temporary residue caused by the audit itself as an operational incident: disclose who/what created it, contain it separately, and do not present its removal as ordinary maintenance savings.
5. When Rodolfo chooses to retain an optional candidate or says to stop cleaning, mark it `intentionally_retained_owner_choice`, cancel any prepared-but-unconfirmed destructive manifest without attempting deletion, remove it from pending/open-item language, and close the cleanup phase. Do not surface it again as a deletion recommendation unless its state materially changes or Rodolfo opens a new cleanup request.
6. If disk headroom is healthy and the remaining recovery is marginal, lead with the operational recommendation to stop rather than continuing to generate destructive manifests merely because a technically redundant target exists.
7. In executive updates, summarize the cumulative story once: what was pre-existing and removed, what the analysis itself created and cleaned up, what was already disclosed and only reclassified, and what is intentionally retained. Do not narrate every intermediate hash as a separate discovery.

## Phase boundary: VPS first, application runtime later

When Rodolfo says **“VPS primeiro; Hermes depois”**, treat that as a hard operational boundary, not merely an ordering hint:

1. Complete the VPS phase through package validation, required or explicitly requested reboot, and post-boot readback before beginning any Hermes port or deployment work. An owner-requested reboot remains a separate acceptance phase even when current and expected kernels already agree; package success does not cancel it.
2. Before that closure, Hermes activity is limited to proving the currently active launcher/version is unchanged. Do not create or promote a port patch, install a candidate venv, run application builds/smokes, or modify Hermes deployment/guard scripts.
3. Distinguish status precisely:
   - `packages updated; reboot pending` = VPS maintenance is **not complete**;
   - `new boot validated; reboot marker cleared; services healthy` = VPS phase complete.
4. If the user asks “deu certo ou não?”, answer the binary state first in one sentence, then name the single pending gate. Do not bury the answer inside a long Hermes/update narrative.
5. A later request to defer Hermes immediately freezes any staged Hermes artifact as inactive evidence only. Verify the canonical launcher still points to the old runtime and do not activate, clean up, or extend the staged port without a new scope.

## Safety and authorization

- Read-only discovery, index refresh, `git fetch`, archive listing, hash verification, and temporary apply checks do not authorize install, restart, retention changes, or deletion.
- A read-only Hermes precheck must resolve both `.venv/bin/python` and `venv/bin/python` from the active launcher, and must not create a full profile archive merely to inspect drift. Full backup belongs immediately before mutation; otherwise a timed-out precheck can manufacture a large invalid archive that becomes a separately confirmed cleanup incident.
- Update, restart, credentials, destructive cleanup, and policy changes follow `AGENT.md` and the Critical Subset confirmation rules.
- When exact package versions, configuration diff, or deletion targets are not observable without temporary privileged access, split the gates instead of asking for one broad confirmation built on historical values. First request only the bounded credential lifecycle and the already-defined non-critical/read-only work; after access, re-freeze the live package transaction, system-file diff, and destructive manifest, then request each applicable Critical confirmation with exact before/after values and rollback. A broad owner request such as “corrigir tudo” authorizes the outcome but does not substitute for unknown `/usr`, system-config, credential, or deletion details.
- Never inspect or print secret contents while sizing or hashing backups. Paths may be named only when that does not expose a credential value.
- Never run `apt autoremove`, delete system-managed `/var/backups`, remove a registered Git worktree with raw `rm`, or shorten backup retention as an incidental part of another cleanup.
- Respect Ubuntu phased updates during routine maintenance. Corroborate deferral with `apt-cache policy <package>` and fresh `apt-get -s upgrade` / `apt-get -s dist-upgrade`; report a phased candidate with no proposed install as a deferred residual, not a failed transaction. Do not force phasing or expand the confirmed package set merely to make `apt list --upgradable` empty; if the package becomes actionable later, freeze it as a new authorization scope.
- Preserve patches, manifests, hashes, final reports, and compact logs when deleting only bulky staging clones or redundant archives.
- Inventory/render generators running inside an auto-versioned repository must create component work directories outside the Git tree. In Hermes sessions, use the canonical profile scratch (`TMPDIR` / workspace), not the system temp directory; standalone privileged jobs may use `/run` when their lifecycle requires it. Record probe paths and do not delete them through implicit trap/finally cleanup: exact disposal still requires the Critical Subset confirmation. Place only the final validated file in the repository via atomic rename. Large JSON components must be passed to `jq` through files such as `--slurpfile`, not serialized into many `--argjson` command-line arguments where `ARG_MAX` can fail.
- After a generator failure, reconcile Git/auto-push before moving or removing temporary artifacts. A concurrent auto-commit can make a formerly untracked temp directory tracked; restore/reconcile first, preserve a hash-validated copy, and apply Critical Subset confirmation before deleting tracked artifacts.
- When an inotify-based auto-commit watcher is restarted after authorized changes were already made, do not assume it scans the existing dirty tree retroactively. Inspect its event mask and batching controls first. Capture the log offset before start/restart and wait for a fresh readiness marker from the current service PID before emitting the catch-up event; a rewrite sent during watcher startup can be missed before `inotifywait` attaches. With a watcher limited to `modify,create,delete,move`, plain `touch` emits only an attribute event and will not advance the batch. Perform one byte-identical rewrite of an already-authorized dirty file only after readiness, prove its hash unchanged, then require the expected commit range, watcher active, scoped status containing only governed exclusions, and `HEAD == origin/main`. If the first event is missed, diagnose readiness and retry once after a new marker instead of spamming rewrites or bypassing the guardrail with a manual commit.
- For retired-agent cleanup, interpret broad language at the **dedicated operational-set boundary**: remove dedicated archive/backup roots only; preserve references embedded in mixed backups, Git, audit logs, and shared evidence unless the user separately names that wider purge scope.
- If the owner explicitly chooses to discard a protected snapshot that contains unique state, disclose the unique classes/bytes and require the Critical Subset double-confirmation with exact roots, file count, bytes, irreversible loss, and what historical evidence will remain.
- Before destructive execution, freeze the authorized target list and verify every target exists, is under an allowed root, has zero process references, is not a mount, and still matches the confirmed type/fingerprint/file/byte totals. A tree target must not be a symlink; an explicitly listed launcher may use a separate `delete_symlink` action after expected-target readback. Use exact paths rather than wildcard deletion, bind authorization to the target-set hash, record an audit start boundary before removing anything, and record a success/partial-failure boundary afterward. Any newly discovered path belongs to a new scope and requires a new manifest and confirmation.
- Before a backup/restore drill, model peak space by stage: ciphertext, decrypted container, extracted component archives, imported profiles/application data, database roundtrip, any preserved failed workspace, and an explicit reserve. Count only artifacts still to be created, but include fresh replay targets; reusing the download does not eliminate a second import's disk cost. Use artifact manifests/archive headers where available rather than an arbitrary size multiplier. After interruption, reconcile processes and workspace before restarting, independently revalidate immutable inputs, and resume the canonical validators without overwriting preserved evidence. Use the “Interrupted encrypted restore” procedure in `references/backup-retention-scope-and-redundancy.md`.
- Report restore acceptance by demonstrated layer: ciphertext hashes, decryption, component checks, isolated profile/application recovery, database archive readability, and database materialization. Never describe `pg_restore --list` as a restored database or a full-bundle label as proof that every application was recovered; these checks exercise different failure modes.
- For a separately authorized deferred-service restart, freeze active sessions and protected service PIDs first. Acceptance requires the named service active, gateway PIDs unchanged, zero `NEEDRESTART-SVC` rows, and no new warning/critical logs. Remaining `NEEDRESTART-SESS` rows normally clear on logout/reconnection and do not justify forced logout, user-manager restart, or reboot.
- For a missing service-owned log under a protected directory, do not grant write to the parent directory as the first repair. Inspect the producer configuration, effective ACL mask, tmpfiles rule and logrotate stanza; prefer exact target creation with the required owner/mode plus a durable rotation `create` rule. If any frozen ACL, mode, file hash or existence state changes after confirmation, stop before mutation and freeze a new manifest rather than widening or reinterpreting the approved scope.
- For generated privileged remote executors, render the embedded payload as a standalone artifact and exercise the same post-check collector once before the first write; syntax compilation alone does not catch undefined names that appear only after mutation. Keep one collector for pre/post validation, and persist a structured remote failure/rollback receipt locally before the wrapper raises so a safe retry can attribute every surviving side effect.
- Any resulting script/config/data/skill change requires the applicable inventory, audit, validation, and REPORT-INFRA closure.

## Executive reporting shape

- Discord completion reports must contain real line-feed characters between sections and bullets. Never send escaped text such as literal `\\n`; inspect the rendered payload or exact outbound string before posting. Lead with the binary outcome, then use short Markdown sections and bullets so Rodolfo can scan the result, practical benefit, validation, cleanup, and residuals independently.

For a focused update-pendency question, lead with the distinction `package updates remaining` versus `post-update activation/restarts remaining`. Name the freshly verified host set, then the exact live remaining gate and recommendation; distinguish historical coverage/migration decisions from newly observed package findings. Zero failed units does not prove that processes loaded the updated libraries. Do not add a backup inventory or reopen unrelated completed phases merely to fill the full report template.

For a combined update-and-backup review, use two sections:

1. **Updates:** closed pendencies, current candidates, service/reboot health, Git release/main distinction, local port risk, recommendation.
2. **Backups:** total by root/set, exact high-confidence deletion paths and bytes, projected disk result, protected/conditional classes, housekeeping coverage gap.

### Answer what can be deleted first

When Rodolfo asks what can be deleted to free disk, lead with the **already validated deletion lot and its reclaim amount**, not the full storage inventory or a reorganization roadmap. State the file class/count, approximate GiB, what recovery remains and whether confirmation or execution is pending. If only one lot passed the gates, say so plainly; directories under review and files merely matched to cloud metadata must not inflate that total.

For a follow-up asking which previously listed categories can be deleted without compromising operation:

1. Reconcile the latest checkpoint and execution receipt before reusing a classification summary; a preparation-time `ready` status can describe a lot already deleted and must not become a new savings offer.
2. Answer in the original category order, with a short verdict for each: **validated lot**, **candidate pending proof**, or **preserve**. Name the removable subclass, the retained boundary and the single missing predicate; do not repeat the whole occupancy inventory or present conditional examples as validated targets.
3. State explicitly when no new lot is validated, without implying that no further reclaim is possible. Separate unchanged current operation from loss of historical recovery, and cache regeneration from zero operational cost; rebuildable does not mean safe to remove while a consumer needs it.
4. Preserve category identity across replies. Treat a shared-hardlink bucket as an accounting reconciliation, not an additional deletion target; if the user refers only to the substantive categories, explain that distinction briefly rather than silently dropping a numbered item.

If he asks for numbered steps, list the actionable deletion sequence first and label every additional category as still under review. When he chooses step-by-step execution, narrow the reply and work to the current lot; after its validated completion, state only the next point, its preservation boundary and whether it is review or approved execution. A request to execute this step and then name the next one does not authorize deleting from the next category. Do not present an eleven-stage investigation as though it were a list of files ready to delete. Keep future retention/prevention separate and secondary unless he explicitly requests that design; do not make an independently safe lot wait for unrelated cleanup research merely to consolidate approvals.

When the current lot is already classified and the next action is destructive confirmation, prepare the stable manifest and exercise its verifier before asking Rodolfo to approve it. Present scope/count, reclaim, retained recovery, irreversible effect and the frozen identifier in one decision message instead of asking first for permission to prepare and then for permission to execute. Preserve the actual Critical gate: an execution request made before the frozen lot was disclosed does not replace its required confirmation; a later plain confirmation of the unchanged disclosed lot is final and must not trigger another generic approval round.

When he says the answer is confusing, immediately narrow to the verified amount and preservation facts instead of repeating the plan. After approval, execute the unchanged exact lot without another approval round. Close with files removed, observed space recovered, current disk/free space and preservation checks; keep hashes, internal paths and governance detail in evidence unless needed for the decision.

When he asks whether deletion affects operation, memory or profiles, answer that precise safety question before discussing more cleanup. Revalidate the frozen lot, prove it does not overlap protected agent/session/browser/production roots, and name the irreversible historical loss separately. Use bounded language such as no impact expected from the checked dependencies; never promise zero risk or equate the ability to run new tests with recovery of their exact old state. A safety question is not approval. Once his later explicit confirmation resolves the unchanged disclosed lot, proceed without asking him to confirm it a third time.

### Local Git history versus remote preservation

When the owner asks why Git history remains on the VPS after a push, distinguish the working copy and `.git` metadata required by current automation from the optional depth of locally retained history. Verify remote refs, local-only commits/changes, `count-objects`, reachable-object disk usage and large-object paths. Zero garbage plus mostly reachable packs means ordinary GC cannot recover that history. Never claim a complete local history is inherently required: a shallow/partial working clone may preserve full remote history, but must be tested against auto-commit/push, rollback, historical-source recovery, worktrees and alternates before a separately confirmed migration. Do not delete `.git` or rewrite remote history as incidental disk cleanup. Identify accidentally versioned media, dependency environments and bulky generated evidence as producer/governance causes, not disposable loose-cache objects.

### Explain a high disk percentage

For a focused **“why is the disk full?”** question, do not force the full maintenance template. Follow this read-only sequence:

1. Resolve what the percentage measures from the current thread's preceding alert before loading unrelated diagnostic branches; disk occupancy, RAM, model context and subscription usage are different metrics.
2. Capture `df -B1 /`, `df -i /` and the observation time. Discover dominant roots with bounded `du`, then build the non-overlapping ledger using audit step 10. Keep GiB and decimal GB explicit and consistent. Reproduce the displayed filesystem percentage using `used / (used + available)` and account separately for reserved free blocks; `used / total` may not match `df` when a reserve exists.
3. Break the largest application root into code/dependencies, operational sources, database dumps, isolated database clusters and copied candidate/stage evidence. Break agent profiles into history databases, artifacts/media, workspaces, browser assets and recovery snapshots. Do not describe a whole application directory as required production data or a whole profile as conversation memory.
4. Demonstrate the dominant producer with one bounded representative completed run and its largest file names/sizes, without opening business or secret contents. Do not select the lexically latest directory without checking it contains output; scheduled no-op runs may leave empty directories. Keep cluster-directory counts distinct from counts of production databases.
5. Compare the latest validated post-cleanup filesystem receipt with the current measurement, and inspect housekeeping filename/root coverage plus its recent log. Report net overall growth separately from per-producer attribution; a current directory total does not establish how much that directory grew since the baseline.
6. Deliver total capacity, occupied/free space and one additive category breakdown first, followed by numbered **Problema, Causa e Solução** findings for the main producers. Explain in plain PT-BR whether the weight is active workload or auxiliary/recovery material. State occupied bytes, proven reclaim and actual savings separately; if deletion eligibility was not validated, say the removable amount is not yet proven. State that the audit did not delete anything, then give one operational recommendation rather than implying a storage-plan upgrade is necessary.

Use `references/backup-retention-scope-and-redundancy.md` for deeper classification and destructive-boundary review.

When Rodolfo asks **only what remained after a cleanup**, answer strictly from a fresh post-cleanup inventory: omit every deleted class/path, avoid before/after narration, and show only current bytes plus whether each residue is removable, conditional, or protected. Keep overlapping roots explicitly non-additive. If he asks which dates remain, summarize current files in date/age ranges with file counts and allocated bytes instead of listing already removed history or every child path.

For residual backup review, distinguish exact duplicates of the live state from historically unique content. A file that duplicates the live state is not individually removable when it belongs to an archive/checksum/restore set whose integrity would be broken. For temporary storage, measure age from the newest descendant in each top-level entry and check live process references before classifying it as abandoned.

A provider-level whole-VPS snapshot may replace overlapping bulky local pre-update archives only after the snapshot is created outside the VPS, provider/account access is read back, and restoration capability is proven. Keep offsite backup as a separate failure domain and retain current local rollback/archives until that gate passes; never substitute a tar of `/` stored on the same VPS and never retire verified recovery paths merely because the snapshot was proposed.

### Provider control-plane credential gate

Classify the available credential by the interface it actually reaches, not by the 1Password item title. A server item containing an SSH target, root/admin username, and server password authorizes guest-OS administration only; it does **not** provide the provider control-plane access needed to create, list, or restore a VPS snapshot. Before changing backup architecture:

1. inspect only non-secret field labels/types and the URL scheme/host;
2. require a validated provider dashboard session or provider API token with access to the exact VPS;
3. create the snapshot and read it back from that control plane;
4. prove the advertised restore capability and retention behavior;
5. only then freeze a separate Critical Subset target set for retiring local archives.

If only SSH is available, report the control-plane gap and leave every verified recovery path unchanged. Do not mislabel an SSH/console password as a dashboard credential and do not attempt to emulate a provider snapshot from inside the guest.

Do not dump thousands of child paths into Discord. Count all files, but list deletion candidates at the exact file or operational-set boundary that would be authorized.

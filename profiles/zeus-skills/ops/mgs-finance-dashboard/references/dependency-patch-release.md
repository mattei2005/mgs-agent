# Financial dashboard dependency-only patches

Use for an explicitly authorized dependency/security update, such as Rodolfo1556897466652037131 (`proxy-addr`2.0.7→2.0.8). Execution evidence/checkpoint, not the authorization itself, establishes publication.

1. Read the exact npm advisory, installed/runtime version, package metadata and affected call sites. Record configured exposure separately from package vulnerability; trust proxy disabled does not mean the installed vulnerable version is patched.
2. Prepare source/fixtures under the normal bounded allowlist, but omit the live `node_modules` symlink. Run a targeted lockfile-only update and a fresh `npm ci --ignore-scripts --no-audit --no-fund` only after proving the isolated candidate has no existing `node_modules`. Never install through a link into active code or run `npm ci` over live dependencies.
3. Diff every package-lock entry and require only the authorized package to change. Verify transitive runtime dependencies are unchanged. Inspect the official runtime patch and seal the candidate dependency files by SHA-256; ordinary release gates hash code/locks but do not seal `node_modules` themselves.
4. Reproduce the security regression against the old package and demonstrate the fixed package rejects it while legitimate inputs still work. For proxy-addr, `/0` is not an accepted test range; use supported broad IPv6/mapped ranges such as `::/1` and `::ffff:0:0/80`, single and multiple subnet lists, native IPv4 and mapped IPv4, plus valid IPv4/mapped/IPv6 controls. These are pure library tests with documentation-range addresses, never traffic against production.
5. Run both complete finance gates on the candidate's own dependency tree and read-only real-snapshot/browser stage. Never reuse a pass from the old dependency tree or change auth/trust-proxy configuration to make a test pass.
6. The permanent release policy intentionally rejects `node_modules`; do not silently widen it. A separately reviewed, task-specific dependency bootstrap can call the canonical publish engine with an exact existing-file allowlist and an equally strict preflight. Retain shared/exclusive admission, legacy locks, backups, remote fencing, budget, hash readback, journal and rollback. Require isolated real-file rehearsal of partial-write rollback and complete commit before production. Do not admit arbitrary package paths, new files, deletions, hooks or system changes.
7. Preserve the remote hidden npm lock's other entries. A production-only dependency tree need not equal the local dev tree: update only the affected package metadata, rather than copying a local hidden lock wholesale. Synchronize root lock, exact official package files, hidden lock and persistent regression tests within one journaled change; changing package.json version alone is not a patch.
8. Restart only the authorized finance application. Verify actual local and remote package versions, fixed behavior, authenticated health/login/MFA/logout, normal screens, finance fingerprints and npm audit. Preserve user sessions and never restart gateways/PostgreSQL or change credentials, grants, firewall or `/etc` as part of a package patch.
9. Record skipped/failed attempts, dependency audit results, retained rollback/test artifacts, inventory/audit and exact REPORT-INFRA readback. Supersede a prior advisory-pending note with the successful release; retain its historical diagnosis.

The bounded bootstrap and tested rollback for the first instance are in `apps/finance-system/private/proxy-addr-1556897466652037131/`; this private example is evidence, not a generic permission to rerun it for another package.

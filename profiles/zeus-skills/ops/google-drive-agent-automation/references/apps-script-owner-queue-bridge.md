## Deployment and acceptance procedure

1. Classify the source/destination through live Drive metadata, verify the approved account/root bindings and keep production enqueue, archive-read cutover, historical processing and source deletion off. Run `python3 scripts/ares_archive_bridge.py preflight` from the repository root.
2. Inspect the owner's current `appsscript.json`; prepare the preserved manifest, explicit scopes and bootstrap scope guard together before asking for the first execution. Preserve Drive v3, timezone, logging and runtime. Follow the OAuth and native-publisher sections below; test privacy-shaped metadata, not just email-visible fixtures.
3. Within the approved scope, run `python3 scripts/ares_archive_bridge.py init --apply`, `python3 scripts/ares_archive_bridge.py publish-worker --apply`, then `python3 scripts/ares_archive_bridge.py enqueue-canary --apply`. Read back the exact folders, source bytes/hash/publisher and immutable request. Capture the job ID from the real enqueue result. Give the owner a bootstrap pinned to those actual outputs, not placeholder or reconstructed identifiers.
4. Have the owner run `mgsArquivoTeste` once. Immediately perform `python3 scripts/ares_archive_bridge.py reconcile --job-id "$JOB_ID"` through the canonical SA to validate the real receipt and both binaries. Only after that passes, run the same command with `--apply` and read back the ACK publisher/body and verified request state. Preserve the request body and reuse an existing marked copy. A first `canaryAcknowledged:false` is expected before this independent ACK exists; do not make the owner repeat consent or rerun the same test to manufacture confirmation.
5. After ACK readback, have the owner run `mgsArquivoAtivar` once. Its internal test must observe that ACK before installing at most one timer. Explain that an empty `copied` list is expected once the canary request is verified. Do not ask for another manual test when the installer already performs the guarded test.
6. Verify scheduled execution through the SA using the heartbeat procedure below; an installer log or screenshot alone proves only installation. If a code repair is needed, publish/verify a new immutable worker, then ask the owner to replace only its file-ID and expected-hash values when the rest of the project is unchanged. Do not resend the whole project, alter the manifest again or request fresh consent for a metadata-only fix.
7. Close only the proven acceptance layer: transport, owner execution, canonical binary/ACK verification, real recurrence, operational intake/consumers, then separately authorized cleanup. Keep the current checkpoint explicit about remaining gates. Report briefly in PT-BR what passed, what is still off and the exact next operator action, if any; after the owner-side phase passes, do not invent further Google clicks.

## Minimal authority-preserving design

- Keep uploads and sanitization in the canonical Shared Drive. Put technical request/receipt files in a dedicated control folder, not the creative candidate pool.
- Have the SA publish immutable, content-hashed JSON requests. Require Google-output `lastModifyingUser.permissionId` to match the pinned native ID of the canonical SA before interpreting a request; pin the owner similarly for receipts/heartbeats. Derive bindings from authenticated Drive `About.user` and the already-approved private archive root's owner, not from a request or its editable properties. Google can hide another principal's `emailAddress`; when visible, it must also match. Missing/mismatched native IDs always fail closed, even if email/displayName looks correct. A property hash alone is not provenance because another editor could rewrite both content and property.
- Bind source Drive/root, archive owner/root, media-only roles, exact sources/parents/hashes and allowed relative paths. Keep the owner worker's request/ACK/heartbeat deletion fields false; any separately approved SA retirement controller has its own explicitly reported activation state. Separate an exact historical canary from future lineage requests; enforce timezone-aware first-seen/source-created cutoffs and never scan old inventory into the queue implicitly.
- The owner worker creates copies in that owner's My Drive. It checks effective account, scope, raw request digest, source state, destination ownership/path and copy integrity, then writes its own receipt. The SA independently streams/verifies both source and copy, records a sidecar mapping and publishes an ACK. Do not replace primary creative IDs or reservations merely because a receipt exists.
- Preserve original/clean lineage, manager reservation and eligibility. Keep source deletion and primary-ID/read cutover separately gated until consumer and human-permission parity pass.

## Explicit OAuth scopes — mandatory before owner execution

Apps Script infers scopes by statically scanning project code. A hash-pinned loader using `new Function`, `eval` or remote source hides the worker's Drive writes from that scan; authorizing the inferred read-only scope again cannot grant a missing requested write scope. An error such as `You do not have permission to call drive.files.create` is an OAuth-scope gate, not evidence that Drive folder Editor access or the account password is wrong. Granular consent may also leave a declared scope ungranted; inspect both declaration and grant rather than blaming the user.

Before the first owner run, explicitly declare `https://www.googleapis.com/auth/drive` and, when the installer manages triggers, `https://www.googleapis.com/auth/script.scriptapp` in `appsscript.json`. Preserve existing timezone/runtime and Advanced Drive v3 dependencies. Add `ScriptApp.requireScopes(ScriptApp.AuthMode.FULL, [...])` in the bootstrap before reading/compiling/executing the worker. Test the manifest and guard together; local mocked Drive success cannot establish Google consent completeness. Full Drive is required for this pre-existing cross-folder source/DriveApp flow; do not choose AppData or `drive.file` merely because the exception lists them as method alternatives.

If the remote manifest has not been read, obtain its current content through the supported owner UI and make a narrow scope edit. Do not replace unknown project settings blindly, revoke grants, delete script properties, rotate credentials, expand file ACLs or create another project to cure a consent loop. Reconcile real request/receipt/heartbeat/copy state before retrying the same request. Explicitly distinguish a locally prepared fix from Google-side recovery verified after consent.

## Publish without exposing credentials or a public endpoint

Publish a versioned worker source blob in the Shared Drive and verify its raw bytes/SHA-256 after upload. Pin that exact source ID, SHA-256, project ID and bounded config in a small owner-side bootstrap. Check the code digest before dynamic compilation. This lets other existing Drive editors cause only a blocked integrity check, not silently replace code executed with the owner's account. A code update requires a deliberately repinned version; never auto-trust a changed source file.

The bootstrap's manual test must be exercised before scheduling. Its installer must require a canary ACK published by the canonical SA, refuse duplicate triggers and create at most one recurring trigger. Do not interpret a prepared installer, local VM test or published code file as a live Google trigger.

## Human access is a separate cutover gate

For Shared-Drive sources, obtain effective access through the paginated `files/{fileId}/permissions` endpoint with `supportsAllDrives=true`; `files.get.permissions` can be absent for those items despite valid inherited access. An absent metadata projection is not proof that all humans lost access. Preserve the failed receipt, diagnose against the exact permissions endpoint, fix only the validator and re-read the same source; never replay copies or grant permissions to clear that false block. Check both source access and destination writer inheritance per copied file.

An owner-account copy inherits its destination access model, not proof of the source's human access. Compare actual source and archive ACLs before read/link/source-cleanup cutover; a successful SA download does not validate any manager's access. Freeze any proposed additions by exact Google-native permission IDs/emails and target roles, preserve owner and SA, and obtain the required explicit sharing decision before granting them. Shared Drive organizer/fileOrganizer roles are not My Drive roles; disclose any proposed mapping to writer rather than call it exact role parity. Keep public/domain sharing and unrelated identities out of the proposal. A sharing approval never authorizes deletion, historical migration or agent/campaign permissions. After an approved grant, read back each exact permission and the complete bounded target set; verify inheritance on every existing copied asset rather than only the parent. Permission propagation can change metadata fingerprints without changing bytes: rerun the exact SA reconciler to force the intended full re-verification and reuse the same requests/copies/ACKs, rather than treating cache invalidation as corruption or replaying copies.

## Content identity versus Google metadata versions

Google documents `File.version` as a counter for every server-side change, including changes not visible to the requester. Do not equate a forward counter advance with a changed media payload, and do not claim its exact cause without evidence. Preserve the original immutable request/version for audit. A safe forward-version acceptance requires the Google-output `sha256Checksum` to equal the frozen SHA-256, with exact source ID, name, MIME, creation time, parent/root, size, MD5 and non-trashed state; backwards/malformed versions, missing native SHA under drift, or any inconsistent content/path field fail closed. The SA must still stream and verify BOTH original and archived bytes before ACK. Never rebase the request, create a replacement candidate or accept MD5/name alone to clear this gate.

Keep active and staged worker versions separate. A verified local fix/source upload does not deploy it into a SHA-pinned owner bootstrap; require owner repin plus a real heartbeat of the staged digest before promoting the active SA config. Keep production flags disabled while that gate is open.

For recurring SA reconciliation, cache only an independently verified job whose current request/receipt/ACK/native publishers and source/archive metadata fingerprints still match. Metadata changes invalidate the cache and require complete binary re-verification; do not re-download every completed video on every healthy timer tick. Use a bounded pending cursor and a rotating completed audit sample, preserving backlog rather than dropping it.

Hermes cron monitor paths on this MGS runtime must be filenames relative to the active profile's scripts directory; an absolute path is rejected despite generic tool descriptions. Read back jobs after a rejected create before retrying. A health monitor should perform deterministic work each tick and emit stable health-only JSON without timestamps/counters, so routine work does not wake an LLM. Healthy agent runs return `[SILENT]`; a real decision-block summary must have an explicit origin-thread delivery route, not disappear into local-only output. Engine traces remain local.

## Cross-principal Drive publisher identity

Request `lastModifyingUser(emailAddress,permissionId)` explicitly in both `files.get` and `files.list`; selecting email alone can yield an empty modifier object across accounts. Verify both directions: the owner reads SA requests/ACKs, and the SA reads owner receipts/heartbeats. The Google User reference documents that email may be absent depending on visibility; the stable native permission ID is Google output, not an editable file marker. Treat IDs as opaque strings and preserve leading zeros. Do not authorize by display name, a body field or an email-only fallback. A changed native ID for the same email is a different binding requiring investigation/authorization, not an automatic pin refresh.

Cover hidden emails, wrong/missing IDs, contradictory visible emails, unknown expected principals and replay of receipt/heartbeat with privacy-shaped fixtures. Verify Google-derived bindings live before pinning. Updating the representation of the same already-approved principal is not an ACL grant or a new authorized user; retain and audit the binding evidence. Publish a new immutable worker version and deliberately repin its file ID/hash; retain the previous version for rollback. Until the owner runs that new pin, its local tests and source publication do not prove Google recovery.

A worker summary with `status:"ok"` but nonempty `blocked` is not a completed archive operation. Require an empty block list, actual per-job receipt, canonical binary verification/ACK and separate scheduled-heartbeat proof at their respective gates.

## Replay, concurrency and recovery

- For a transient `DRIVE_HTTP_500`, first read the exact failed tick and distinguish an older `automation-last-error.json` from the current failure. Under the existing queue lock, verify the same request/receipt/ACK IDs, immutable bytes and publishers, then fully stream both source/archive pairs before treating the error as transient. Do not change code, frozen requests or owner pins solely for a recovered provider 500. With active retirement, inspect the implementation before using `--reconcile-only`: its temporary `queue_enabled=false` producer config can fail `RETIREMENT_ACTIVATION_NOT_PINNED`. A bounded recovery may use the existing internal cycle with `allow_retirement=False`, intake-state → queue lock order, zero eligible production rows checked first, and an in-memory Drive guard rejecting every non-GET request; preserve live flags and validate the written tick plus intake/native-job health. This validates transport recovery without authorizing production, backfill or deletion.
- Use one local producer lock plus the worker's script lock. Immutable request bodies and separately owned receipts avoid competing writers on the same JSON content.
- Derive job identity from frozen source IDs/checksums/paths, not a fresh request timestamp. Reuse the original local/remote request on retry and verify exact content.
- Mark intent before a non-idempotent copy. A lost response must reconcile a landed marked copy; if none is visible, stop instead of replaying blindly. Completed jobs/receipts must reuse the same archive IDs.
- After canonical verification, let the SA mark the request metadata verified so the worker polls only queued requests; preserve the immutable body. This avoids rescanning every completed job indefinitely.
- Reset per-item `job`/`prior` state at the start of every JavaScript loop iteration. Function-scoped `var` can otherwise carry a trusted previous job into a later untrusted request's error handler and overwrite the wrong receipt. Cover this with an interleaving regression.
- Release locks in a nested `finally` even when budget/state persistence fails. Invalid budget state must fail closed, not reset runtime accounting. Bound jobs per tick, execution time, rolling runtime budget, retries and provider cooldowns.

- Emit an owner-authored heartbeat with the pinned worker hash, timestamp, work/error summary and the installable event's `triggerUid` when present; keep it null for manual runs. After installation, use a bounded read-only foreground probe to observe two fresh scheduled heartbeats with the same nonempty trigger UID, expected code hash/native publisher, empty block list, ACK true and deletion false. Retain both timestamps and calculate their interval with code. Measure cadence between scheduled events, not from installation to the first event, because initial dispatch may occur before a full nominal interval. Allow small dispatch jitter and report configured versus observed cadence separately. Do not ask the owner to keep clicking Run or recreate the timer when a bounded probe has not yet seen it; inspect the exact trigger execution record if the grace window expires.

A paused `queue_enabled=false` stage is intentional deployment state, not active unattended intake. Keep transport, timer, reconciler and business-flow readiness separate in checkpoints and reports.

## Whole-drive scope expansion and reversible owner probes

When the owner expands a creative-only migration to the entire Shared Drive, inventory all active objects by paginated `corpora=drive` listing and reconcile ancestry, not just the visible root or creative manifest. Snapshot native Sheets metadata/formulas and discover consumers before deciding whether to move IDs or copy/replace them. Treat encrypted disaster-recovery files as a restricted recovery class: a destination creative parent with more collaborators is not ACL parity. Preserve producer, verification, retention and restore routes; copying today's backups alone is not an automated cutover.

Keep a new owner probe separate from production migration. Pin its exact SA manifest and allow no production mutation, delete or ACL grant. If checking native cross-drive ID preservation, use only one explicitly tagged synthetic resource, a durable move intent, exact native owner checks, immediate restoration, and landed-state reconciliation after a lost response. Preserve a recovered receipt as terminal/no-replay rather than moving again on every timer. Promote a deliberately repinned digest only after the native receipt, live canary restoration and fresh scheduled heartbeat agree; update both general and historical digest bindings under the same queue lock, with rollback if either write fails.

After a successful Drive create, persist and validate the returned ID with `files.get` before relying on property-indexed `files.list`; a lagging search index is not evidence that creation failed and never authorizes a second POST. Read back the landed exact object first, reuse it, and keep the original intent/receipt.

Bind a Shared Drive's virtual root through `drives.get(...fields=id,name)` and the exact opaque drive ID, not its `files.get.name` label: the root can appear as `Drive` on one metadata surface and the actual drive name on another. Keep non-root names and every ID/MIME/parent/driveId gate strict. Emit mismatched target IDs and field names into an owner-authored blocked receipt before an optional probe exception can prevent the heartbeat. Preserve any detailed restore-failure receipt; cap repeated probe attempts and require real owner execution before claiming recovery. A generic SOURCE_CHANGED exception alone does not prove which field differed.

Treat a missing My Drive `parents` projection for the SA as unavailable information, not a proven empty parent set. For an exact approved archive-root ID, prove the owner's visible parent equals the authenticated owner's `files.get('root')` ID, with matching owner and folder MIME, before accepting the privacy-shaped difference. Never generalize this exception to source files or accept an arbitrary destination parent. Cover SA-hidden/owner-visible parent, wrong root, wrong owner and missing owner-visible parent in fixtures. If any whole-drive probe is blocked, set the top-level worker status to blocked as well; transport progress does not make an incomplete migration successful.

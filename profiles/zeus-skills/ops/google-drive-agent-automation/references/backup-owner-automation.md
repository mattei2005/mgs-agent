# Backup owner archive automation

Use for the approved future-only backup lane; this is not Google agent OAuth fallback or permission to delete backups.

## Owner/SA boundary and acceptance

- Keep the canonical SA uploader, original `_DISASTER_RECOVERY` root/tier IDs, config hash, cadence and source policy unchanged. Freeze a separate immutable backup plan with exact source/archive folder IDs, owner/SA native permission IDs, approved corporate ACL and a Google-created-time future cutoff. Historical migration is a separate manifest; never enqueue it implicitly through future discovery.
- Let the canonical SA publish exact content-bound requests; verify native SA publisher plus raw digest/root/type on the owner side. Private `appProperties` are application-scoped and need not be visible to the owner Apps Script project: the SA freezes its managed metadata, the owner validates native content/ancestry, and the SA verifies those private properties again after the move. Never use editable metadata alone as authority.
- Keep the backup move in the existing script lock and unchanged bulk runtime ledger. Admit at most one move before the existing media scan after its account/root/budget gate; a heartbeat hook may serialize the result but must not execute the lane again. Verify the actual call order before claiming backup priority: a hook before media-request listing can still run after expensive historical folder preparation. Inspect remaining-budget reservation and durable folder progress when diagnosing starvation; use the runtime-pause procedure in `apps-script-owner-queue-bridge.md` rather than assuming a healthy timer guarantees backup capacity. A bulk pause remains a pause. Manual control performs read-only owner/path/pilot-capability validation only. Preserve accounting; change the runtime ceiling only under explicit authorization and the verified provider account class. Never install a second trigger or move arbitrary files merely to prove scheduling.
- Give every request an exact SA-created receipt slot. Validate its scope/schema/publisher before moving, persist an exact-ID move intent first, and publish the owner receipt into that same slot. A lost move response is reconciled through native location/content; an unlanded durable intent is blocked, never replayed blindly. Preserve receipt publication journals and resume publication after a landed move without moving or rolling back again.
- Journal plan/source/request publication before POST. Reuse exact returned IDs and immutable raw bytes; an unresolved create can be adopted by its exact trusted key but must not trigger another POST when lookup remains empty. Native publication plus local tests is staged code, not owner deployment.
- Treat an absent/null/non-object `backupArchive.probe` as pending acceptance, not success or an exception. Validate both the backup section and probe as objects before `.get`; an `ok` scheduled heartbeat can legitimately lack the probe when its remaining-budget reservation skips that lane. Cover `probe:null` with every preceding readiness gate satisfied, because a manual/paused fixture can short-circuit before the faulty access. Require the complete native probe before any pin/activation write; test that missing evidence cannot call the acceptor or persist samples.
- Require deliberate owner repin and two distinct fresh scheduled heartbeats of the new digest/native trigger with a successful read-only backup probe. Then use the existing full whole-drive acceptor to promote both SA/historical pins; only afterward may a canonical-SA activation enable the future-only move producer. Keep old pins/local state for rollback.
- Independently re-read request and owner receipt, verify the same physical backup ID, intended owner/parent/ACL, all frozen native checksums and SA-visible managed properties, stream the archived ciphertext once, publish/read back an SA ACK, and cache only while the current metadata/receipt/request fingerprint matches. Expose the first real verified backup as a stable monitor transition; do not ask for another human pilot to manufacture acceptance.

## Validate the live flow now

Use this sequence after owner setup or repinning is complete and the original authorization covers acceptance and future-only archiving.

1. **Read the native state first.** Through the canonical-SA helper, load the backup plan/stage, current owner heartbeat and backup job state. Check the staged digest, native publisher, original trigger, freshness, ACK, empty block lists, actual probe and runtime telemetry. Compare persisted scheduled samples with the latest heartbeat; a second qualifying event may already exist even if the monitor has not run yet.
2. **Run the existing acceptance/producer.** From `/root/mgs-agent`, execute `python3 scripts/mgs_backup_automation.py tick`. Its existing `resume_acceptance()` records distinct scheduled samples, invokes the full whole-drive verifier, promotes both active pins and publishes future-only activation only after all gates pass. Read back the exact activation file and require `archiveMovesEnabled:true`, `archiveTrashEnabled:false`, `deleteSource:false`, the approved plan/digest and native SA publisher. Do not bypass the verifier by flipping flags manually. Use `preview` for inventory-only diagnosis, not as proof of productive execution.
3. **Freeze the first real queued request.** Read its exact remote body and receipt-slot IDs, verify the publisher and frozen backup metadata, and retain its stable job/file IDs. Select an existing eligible future backup; do not ask the owner to upload a fixture or implicitly enqueue historical data. Enqueueing proves producer readiness, not successful archiving.
4. **Observe the original scheduler.** Poll the owner-authored heartbeat in a bounded foreground window with one read-only Drive client, reusing its token. Persist only changed native observations so an overwritten heartbeat does not erase evidence. Stop when the exact queued job appears in `moved`, a real blocker appears or the window expires. Do not invoke the manual probe as scheduled proof, add a trigger, reset usage or force a parallel move. If observation expires, preserve the exact pending job and existing monitor route rather than claiming success.
5. **Exercise the real reconciler.** After the move, run the same `tick` command again. Require its successful full ciphertext stream comparison of size, MD5 and SHA-256, plus native same-ID destination/owner/ACL/private-property checks. Read back the owner receipt, SA ACK and request's `verified` marker individually. Recompute the request/receipt/current-metadata fingerprint and compare it with the stored post-stream fingerprint; do not substitute native checksum metadata alone for an actual stream. Reuse a valid verified cache rather than downloading the same large backup again solely for presentation.
6. **Prove continuation and reconcile state labels.** Read the next queued job, monitor enabled/scheduled/error state and both active pins. Advance stages/checkpoints from owner-repin-required to scheduled acceptance and first-real-backup-verified as evidence arrives, so later monitors do not request completed Google clicks. Keep activation, first successful real archive and full historical migration as distinct statuses.
7. **Report the proven layer.** State whether future backups now run automatically, cite the real archive time/size and integrity result, and say whether the owner has any action left. Keep historical migration and destructive retention explicitly separate. A verified ciphertext archive proves transport integrity, not a new decrypt/restore drill or guaranteed unlimited future capacity.

## Retention is a different gate

Generate retention preview across source and archive IDs without duplicates, using unchanged per-tier counts. Keep source-expired/unverified data and the last restore-proven generation protected. A preview candidate is NOT a trash command. Do not implement/activate owner deletion or reinterpret `canEdit`/`canDownload` as `canTrash`; separately confirmed archive-retention mutation is still required.

## Confirmed private-owner retention execution

After the separate destructive confirmation, keep retention in a **separate versioned policy** rather than rewriting immutable historical move plans/ACKs whose trash flag was false. Use the approved tier counts, trash only, and protect both the pilot and the latest actual isolated PASS restore generation. Compute the union of source/archive IDs without duplicates; preserve source-expired and unverified files. Accept current direct-to-archive backups only through their exact native canonical-SA direct-upload ACK, full-stream proof, parent/root and checksums—not the owner slot alone. Immediately before each bounded trash RPC, recompute eligibility/protection, verify the exact native ACK and metadata/version CAS, journal the intent, and read back the same ID through owner and SA with `trashed:true`, unchanged bytes/properties/parent and no permanent DELETE. Reconcile an unknown outcome without replay. Preserve recurrence on the existing monitor and distinguish confirmed/active policy, actual trash execution, zero-current-candidate validation and the independent move lane's still-immutable trash-disabled contract.

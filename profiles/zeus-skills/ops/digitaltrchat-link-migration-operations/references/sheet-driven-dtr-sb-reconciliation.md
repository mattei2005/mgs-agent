# Sheet-driven DTR ↔ Smart Bidding reconciliation

Use this procedure when Rodolfo defines the audit population from an operational Sheet and wants a per-Page relation across DigitalTRChat and Smart Bidding, including whether the DTR template is installed.

## Phase 1 — source and credential closure

1. Read the exact spreadsheet ID and `gid` through the canonical MGS Service Account and Sheets API. Validate both Drive `files.get` and Sheets `spreadsheets.get`; never use public CSV/GViz for operational scope because an active filter can silently hide rows.
2. Resolve the `gid` to its tab title, read the full bounded range, validate the required `User` and `Segurador` headers, and preserve every row occurrence. Do not deduplicate repeated Sheet rows; deduplicate only the login list used for credential preflight.
3. Extract exact `User` emails and refresh the 1Password DigitalTRChat inventory by username. Require a readable username and a non-empty password field without printing either credential.
4. When multiple items carry the same username, do not choose by title alone:
   - compare password values only in process memory, never print values or hashes;
   - if values are equal, select one stable canonical item ID and record the duplicate as harmless inventory drift;
   - if values differ, probe each item in a separate isolated DTR browser context and select only an item whose real login succeeds;
   - classify zero valid items or more than one unresolved valid identity as a blocker. A stale generic-title item is not a missing login when a canonical item succeeds.
5. Reconcile `unique Sheet users = resolved + missing + incomplete + unresolved`. If Rodolfo authorized only Phase 1, stop here and report the exact missing identities before any Page scan.

## Phase 2 — exact login, segurador and Page inventory

1. Process every Sheet occurrence independently as `User + normalized Segurador`; the same login may contain several imported Facebook accounts.
2. Log in with the Phase-1-resolved immutable item ID, enumerate `a.account_switch[data-id]`, and select the exact Segurador from the Sheet. Distinct account IDs with the same normalized name remain ambiguous unless the Sheet or live Page identity resolves them.
3. After switching, reload the account-scoped Page inventory and prove the context changed. Use `/social_accounts/index` and its `.page_list_ul` cards as the complete imported-Page population authority; the Bot Manager Page selector can omit disconnected or not-yet-scanned Pages and therefore cannot define a full DTR↔SB ID audit. Enumerate every Page as:
   - Page name;
   - DTR internal `PAGE_ID` (small ID);
   - Facebook `FB_PAGE_ID` (large ID);
   - exact login and imported account ID/name;
   - webhook state derived from `disable_webhook` versus `enable_webhook`.
   Keep Bot Manager visibility only as a separate readiness field. Reconcile by exact large ID even for disconnected cards, but place those Pages in a separate no-auto-correction partition until their connection state is decided.
4. Normalize Page names to Unicode NFC only for comparison. Preserve the literal IDs as strings; never reconstruct a long Facebook ID from scientific notation. A Social Accounts card may append a Page username after `FB_PAGE_ID | PAGE_ID`; parse the two numeric IDs before that optional suffix rather than rejecting the Page or treating the suffix as part of the small ID.
5. Keep three post-reconnection states separate instead of treating Page presence as proof of readiness:
   - a Page card under `/social_accounts/index` proves the Page was imported and has a DTR internal Page ID;
   - a card control whose class contains `disable_webhook` means the webhook is currently enabled/connected, because that control's action would disable it; a control whose class contains `enable_webhook` means the Page is still not connected;
   - an empty Bot Manager Page selector can remain legitimate until the operator completes the separate `Scan` and `Migrate` recovery steps. Record Bot Manager visibility separately and never use it alone to negate a proven webhook connection.
6. When validating a manual reconnection batch, require every imported Page card to have `disable_webhook`, report the exact Page names plus large/small IDs for any `enable_webhook` remainder, and perform no click unless connection writes were separately authorized.
7. For the current MGS full-portfolio recovery sequence, `Scan` and `Migrate` are a dedicated **final phase across every Page**. Do not interleave them with insurer identity closure, webhook connection, SB ID reconciliation or template installation merely because Bot Manager is still empty after reconnection. This ordering remains in force unless Rodolfo explicitly changes it for a later scope.
8. Reconcile the global ignore list by `FB_PAGE_ID` before requiring webhook completion. The canonical `/root/mgs-agent/data/mgs-global-page-ignore-list.json` currently stores Page records in the top-level `entries` array; read that exact schema and fail closed if neither the expected array nor an explicitly versioned successor exists. Never silently default to an empty ignore set because a legacy parser looked for `pages`: that can reintroduce a globally ignored Page into connection, scan or audit denominators. Treat a current direct statement from Rodolfo that a Page is `Blocked` or must be ignored as a canonical exclusion decision: add or update exactly one entry by large ID, preserve the source message and current small ID, validate the entry count by readback, and then rebuild the batch denominator. Reconnection can preserve the large ID while regenerating the internal Page ID; when Rodolfo reconfirms an already-ignored Page, update the existing ignore entry's current `page_id_pg`, preserve the previous value as history, and never create a duplicate entry for the same large ID. Exclude ignored Pages from the effective connection denominator and from every later scan, registration, template, scheduling and `Scan`/`Migrate` batch.
9. Classify imported-account resolution by exact candidate count, not by Page count: zero candidates is `account_missing` (never `ambiguous`); one normalized-name candidate closes the identity even when it has zero Pages, which is valid `no-pages`; two or more candidates is `duplicate_account`/ambiguous until Page identity or an explicit decision selects one. Preserve every unresolved Sheet row and its displayed Page count as unobserved scope; never let it disappear from app-level totals merely because no live DTR Page could be enumerated. A direct switch to a historical account ID returning HTTP 200 does not resolve the account when the account remains absent from the live switcher or reload returns zero Pages; keep it `account_missing` because the switch transport can succeed without restoring an imported-account identity.
10. Close the identity/connection phase only when every Sheet insurer has exactly one imported-account identity and every non-ignored imported Page has webhook state `disable_webhook`. Then rerun the full live DTR↔SB reconciliation before any SB correction, because reconnection can make all previously reported small-ID and UTM counts stale.

## Full-portfolio zero-state rescan

Use this branch when Rodolfo asks to rebuild the complete B001–B013 DTR↔SB result from live state, page by page, without carrying a prior snapshot forward as the population source.

1. Read the active Sheet again and close every current `User + Segurador` identity. Enumerate every live DTR Page from `/social_accounts/index`; do not start from the previous problem list, prior reconciliation JSON, SB-only rows, or the current disconnected set. Preserve old artifacts only as rollback/evidence.
2. Capture the full live SB `Accounts > Messenger > Page` scope with every current `Digital trust` and `Digital trust 2` site selected. Repeat that read in a fresh authenticated context and require the selected site set and row population to remain stable. Join DTR to SB only by exact `FB_PAGE_ID`, then compare small `PAGE_ID`, `UTM_CAMPAIGN=pg_<PAGE_ID>`, name, login, status and connection as separate dimensions.
3. Do not exclude `On-hold` or `Blocked` from liveness inspection when the current instruction says to inspect all statuses. Status is not liveness. Keep the canonical global-ignore axis separate: an instruction to inspect status partitions authorizes read-only recovery checks but does not remove an ignore entry or authorize writes to it. Report online ignored Pages as an explicit decision cohort.
4. Partition every disconnected Page through live evidence in this order:
   - exact Page visible in the current app/account token's `/me/accounts` → online and technically connectable, subject to the global-ignore gate;
   - absent from `/me/accounts`, then explicit unavailable-content result at `https://facebook.com/<FB_PAGE_ID>` in AdsPower → blocked/removed/down; do not connect or scan;
   - Facebook Page opens, but the exact ID remains absent from `/me/accounts` → online but missing Page tasks/access; report the access blocker and do not replay the webhook;
   - ambiguous Facebook result → retain as unresolved and make no write.
5. Connect only online, non-ignored candidates. Use one webhook canary per imported account, require application success plus fresh `disable_webhook` readback, and continue best-effort only when Rodolfo authorized isolated skips. After connection, rebuild the DTR inventory because the mutable small ID may have changed.
6. Repair SB only after a unique large-ID join. Change only the authorized small `PAGE_ID + UTM_CAMPAIGN` pair and make zero writes when both are already canonical. Missing SB rows, Page renames, status changes and profile association remain separate scopes unless explicitly authorized.
7. For an explicitly authorized portfolio Auto Scan that includes all statuses, freeze the final connected, non-ignored DTR population and submit exactly one job per Page—including `On-hold`, connected `Blocked`, already-connected Pages and connected Pages missing from SB. Keep ignored Pages and disconnected/down Pages out of the submission set. Journal each accepted Page immediately by immutable large ID, small ID, imported account, attempt and HTTP result.
8. Make the writer resumable before its first submission. On wrapper interruption, read the immutable manifest and journal, refresh the live identity/connection gate, and resume only IDs with no accepted event. A safely resumable writer must load accepted IDs and skip them; never rerun a non-resumable writer or enqueue an already accepted Page merely to obtain a final summary.
9. Close with fresh, independent reads of the full Sheet, all DTR accounts and the complete SB scope. Require a stable source hash, identical DTR identity set, exact final connection partition, zero unresolved small-ID/UTM drift, and `accepted IDs == scan manifest IDs` with no extras.
10. When Rodolfo asks for only problem Pages, report disjoint exception groups that reconcile to the live total: Facebook unavailable, online but absent from `/me/accounts`, online/Graph-visible but globally ignored, connected but missing from SB, ID/UTM mismatch, connection failure and Auto Scan failure. Group by app and Segurador; print Page name, small ID, large ID, current SB status or `sem cadastro SB`, and ignore state. Do not list clean Pages.

## Named cross-app Segurador batches

Use this branch when Rodolfo names Seguradores rather than one app and requests analysis plus Page-ID repair, connection, and Auto Scan.

1. Normalize each requested name only for comparison, then resolve it against current active Sheet rows (`NO APP`, `Removidos acumulado != X`). Do not substitute a similarly named insurer or reinterpret a historical Page name as a current Segurador. For a name with no current row, search current DTR account switchers and current SB by exact identity; use historical reports only to classify the old object as removed/Blocked, never to reintroduce it into production.
2. Group resolved rows by their current exact app generation, run one complete read-only audit per app, and merge only error-free artifacts. Retry a transient login/navigation failure once with a fresh context; never merge a partial artifact whose summary contains errors. Freeze source hashes, current app labels, exact Sheet rows, and the requested-name resolution table in the cross-app manifest.
3. Join current DTR Pages to the full two-company SB scope by exact `FB_PAGE_ID`, then compare all structural fields: DTR/Sheet login versus effective SB login (`USER_LOGIN` or `LOGIN`), Page name, imported account, and unique SB row. Apply Blocked/global-ignore exclusions only after that join and publish a waterfall of requested names → current names → observed Pages → exclusions → structurally eligible Pages.
4. Resolve source authority before classifying login drift. By default, an effective-login mismatch is `NAME_OR_LOGIN_MISMATCH` and blocks the complete requested batch. If Rodolfo explicitly declares the current Sheet login authoritative, use that exact login for DTR and reclassify the mismatching SB login as `STALE_SB_LOGIN_METADATA`: a unique exact `FB_PAGE_ID` remains the Page join, and the repair payload must omit `LOGIN`, `USER_LOGIN`, profile association and Page name. Preserve and read back those fields byte-for-byte while changing only the authorized `PAGE_ID + UTM_CAMPAIGN`. Under this explicit authority, a Page-name mismatch is a preserved diagnostic when the large-ID join is unique; it does not authorize renaming the row. Still stop on absent/duplicate large IDs, unresolved Sheet/DTR accounts, or any identity that depends only on Page name or small ID. Never silently process a reduced remainder because that is a scope reduction.
5. After the identity set is closed, connect every eligible disconnected Page first, with one canary per imported account and an all-connected gate. A later account can fail after earlier accounts have already connected: journal and independently read back the proven successful connections, do not roll them back merely to recreate an all-old state, but block all SB correction and Auto Scan stages until the exact eligible target set is connected or Rodolfo explicitly changes the scope. Rerun the live DTR↔SB audit because reconnection may change small IDs; only then update the proven editable pair `PAGE_ID + UTM_CAMPAIGN`. Finally submit one Auto Scan for every eligible Page in the frozen batch, including Pages that were already connected. Keep DTR targets/jobs and SB rows validated as separate denominators when Pages are missing from SB.

## Direct Blocked classification and batch continuation

When Rodolfo identifies named Pages as blocked during a connection/Auto Scan batch, treat that message as both a canonical exclusion decision and an explicit reduction of the active batch:

1. Freeze each named Page by `FB_PAGE_ID + PAGE_ID + Page name + login + Segurador`; never expand a Segurador-level statement to its other Pages.
2. If Rodolfo asks to mirror the decision in Smart Bidding, fetch the full live Messenger scope, require exactly one row by `FB_PAGE_ID`, and verify Page name and current small ID. Back up the complete row after recursively removing secret-bearing keys. Build the save from supported editable fields, change only `STATUS=Blocked`, omit join/read-only fields (`PUBLISHER_ID`, `LEADS`, `PROFILE_NAME`, `LOGIN`, `USER_LOGIN`) and optional null fields, and preserve every non-null template/message/schedule field—especially `BROADCAST_LAST_SCHEDULE`. Use one reversible canary and require fresh readback with every non-status field unchanged. If the POST returns an error, treat the state as unknown: read back the exact large ID before retrying; accept it if `Blocked` already landed, retry once only if the entire old row remains intact, and rollback the proven changed subset on partial state or preserved-field drift. Close the batch only after a new authenticated session proves every target `Blocked` with zero small-ID or preserved-field drift. Do not alter `RESTRICTED_UNTIL`, IDs, login, profile association, Notes, template fields, schedule, or campaign metadata.
3. Add or update exactly one global-ignore entry by `FB_PAGE_ID`, preserve the source message and current small ID, and read back one unique `BLOCKED` entry. When an entry already exists with an older small ID, preserve that value as history rather than creating a duplicate.
4. Rebuild `requested = Blocked/global-ignore exclusions + remaining eligible`. The direct Blocked classification is the new scope decision, so continue the remaining eligible Pages under the original connection/Auto Scan authorization without another scope question. Never submit a connection or scan for the excluded Pages.
5. If the active Sheet assignment changes concurrently, do not restore or reassign the Segurador. A direct Page-level Blocked instruction may still update a unique existing SB row by exact `FB_PAGE_ID`; report the source drift, preserve the new Sheet assignment, and never use the status write to recreate profile ownership.
6. Rerun the app audit after both surfaces converge. Require the new Blocked count, ignore-list matches, remaining disconnected set, and zero ID/UTM drift to reconcile before continuing.

## Webhook connection canary and stale Meta Page access diagnosis

Use this branch before Auto Scan when Rodolfo authorizes connecting an exact disconnected-Page batch.

1. Freeze the requested Page set and global-ignore exclusions, partition it by imported account, then use one non-ignored Page as a connection canary **inside each account** before touching that account's remaining Pages. The UI-equivalent request is `POST /social_accounts/enable_disable_webhook` with `page_id=<DTR_PAGE_ID>`, `enable_disable=enable`, `restart=0`, the Social Accounts Referer, and `X-Requested-With: XMLHttpRequest`. A canary from one Segurador/account does not validate another account's Meta access.
2. Require all three success signals: HTTP 200, a response body that does not report `status=0`, and a fresh `/social_accounts/index` readback whose exact Page card now exposes `disable_webhook`. HTTP 200 with `status=0` is an application failure, not a successful connection. Journal the sanitized response and never continue merely because the transport succeeded.
3. Treat `Error validating application. Application has been deleted.` as a Page-token/access diagnostic, not proof that the currently assigned Meta app is itself deleted. Stop the batch after the canary and diagnose in this order:
   - resolve the exact current generation and app ID from the canonical registry/Sheet, then reconcile the latest monitor state, pause state and audit evidence for that same app ID;
   - verify the expected current app independently through Graph `/{app_id}?fields=id,name`; a fresh same-generation monitor/Graph success means the canonical app is healthy, so classify the DTR response as a stale DTR application/OAuth binding pending token diagnosis rather than reporting the current app deleted;
   - extract the selected DTR account's active user token only in process memory and inspect it with `/debug_token` using the expected app credentials;
   - call `/me/accounts?fields=id,name,access_token,tasks&limit=200` with that active user token and compare every requested `FB_PAGE_ID` exactly;
   - for a requested Page that is visible, inspect its Page token with `/debug_token` and read `/{FB_PAGE_ID}/subscribed_apps` before deciding whether the problem is account-level or Page-level.
   Never print, persist, hash or include any user/Page/app token or app secret in an artifact or report. Replacing/reconnecting the DTR application binding changes OAuth credentials/tokens and therefore requires the Critical Subset confirmation; the original authorization to fix IDs, connect Pages and trigger Auto Scan does not authorize that broader repair.
   Run the reusable sanitized gate instead of rebuilding this probe ad hoc:
   `python scripts/diagnose_dtr_page_access.py --app <CURRENT_APP> --app-item-title '<EXACT_1P_TITLE>' --helper <OPERATION_HELPER.py> --targets <FROZEN_TARGETS.json> --out <MODE_0600_REPORT.json>`.
   The helper must expose the proven DTR login, credential-resolution, account-switch, and inventory functions used by the frozen operation; the target manifest must carry `bot_user`, `account_id`, `segurador`, `page_name`, and exact `fb_page_id` strings.
4. Partition the result instead of repeatedly submitting the same connect request:
   - current app live + account token valid for that app + requested Page absent from `/me/accounts` → the active Facebook identity no longer exposes that Page; reconnect/re-authorize the profile/Page before retrying DTR connection. If the DTR webhook response says the session/token is invalid but fresh `/debug_token` proves the current-app account token valid, trust the layered Graph diagnosis: the absent exact Page means missing Page tasks/access, not an invalid current token, and replaying the webhook cannot restore that access;
   - account token invalid or checkpointed → complete Facebook reauthentication/checkpoint recovery before any Page connection attempt;
   - requested Page visible with a valid current-app Page token but no subscribed app → describe it plainly as “Facebook access is valid, but the DTR webhook is not connected,” not as a bad token or deleted current app. Keep it as a separate Page-level connection candidate; once every other target is either reachable or explicitly excluded, submit the normal DTR webhook connection canary for that Page, require fresh `disable_webhook` readback, and only then run its authorized Auto Scan. Do not infer that other missing Pages are equally repairable;
   - current app itself unavailable/deleted → stop and escalate the app assignment rather than changing Page rows.
5. A deterministic Graph/application error is not transient: do not spend the retry budget replaying it. Retry a connection only after the underlying account/Page access changed and the full identity gate passes again. After an operator reports a manual AdsPower/DTR reconnection, rerun both `/debug_token` and `/me/accounts` before replaying the webhook request: a refreshed current-app account token does **not** prove that the target Pages were restored. If the token is now valid but exact requested Pages remain absent from `/me/accounts`, classify the reconnection as account-token recovery only and require Facebook Page tasks/access to be restored for those Page IDs; another DTR login or webhook retry cannot repair missing Page access.
6. Preserve exact-batch semantics. If only part of the authorized population remains reachable, do not connect that subset or run Auto Scan on it without a new scope decision. Require a fresh gate proving every eligible Page connected before the first Auto Scan submission. If Rodolfo then explicitly authorizes a best-effort/reachable subset, freeze a new disjoint partition (`global-ignore`, `already connected`, `connection candidate`, `access-blocked`) before writing. Use one non-ignored connection canary per imported account, stop repeating a deterministic application failure within that account, and submit Auto Scan only for Pages whose exact live card proves a connected webhook; report every blocked Page by name and both IDs.

Preserve Sheet row, exact `User`, Segurador and displayed page count.
2. Resolve every distinct login, then emit one account result for **every selected Sheet row**, including `account_missing`, `duplicate_account` and `no_pages`. Never omit an unresolved Segurador from the denominator merely because no account candidate was found; omission makes the insurer and Page totals look falsely complete. Keep `live DTR Pages observed in resolved accounts` separate from `Sheet-declared Pages not observed because their account is unresolved`; do not add those numbers into one verified Page total, and do not call the app audit complete until the unresolved account identity is closed.
3. Enumerate live DTR Pages from `/social_accounts/index`, including webhook state. In SB `Accounts > Messenger > Page`, select every current site under both `Digital trust` and `Digital trust 2`, then capture/replay the resulting `/campaigns/Messenger` request.    - DTR Page with one SB row and a different small ID → `SMALL_ID_MISMATCH`;
   - DTR Page with no SB row → `MISSING_IN_SB`; because no SB row means no SB status, cross-partition these Pages by live webhook state and global-ignore membership instead of labeling them `Blocked` or borrowing status from another source;

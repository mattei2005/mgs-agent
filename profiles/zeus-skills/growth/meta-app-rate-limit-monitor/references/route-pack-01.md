## Overview

This skill captures the MGS procedure for monitoring Meta/Facebook Developer apps used by Messenger/ChatPion/DigitalTrChat, especially the B001–B011 app split created to reduce rate-limit and restriction risk.

The operational model is:

```text
Facebook profile / segurador → pages → Messenger bot user → Meta Developer app B001–B011
```

For Openzed, the current approved allocation is:

```text
B007 = Openzed isolated app
```

If B007 starts hitting rate limit or operational delivery issues, Rodolfo may split Openzed back into two apps.

## When to Use

Use this skill when Rodolfo asks to:

- monitor whether a Meta Developer app is healthy, blocked, restricted, or rate-limited;
- validate a token saved in 1Password for apps like `BOT B007 Token`;
- decide which Graph API permissions are needed for monitoring;
- explain whether one token can monitor apps or whether tokens are needed per segurador/profile;
- create a future cron/alert for B001–B011 usage;
- investigate Openzed/B007 app health;
- distinguish real app rate-limit telemetry from operational symptoms in SB/DigitalTrChat/ChatPion.

Do not use this as the source for campaign/media-buying decisions. This is infra/ops telemetry for app health and restriction risk.

## Key Distinctions

```text
Question                                      Answer
--------------------------------------------  -----------------------------------------
Monitor app rate-limit headers                Token from app admin/dev user is enough.
Need token per segurador for app headers       No.
List pages inside each segurador/profile       Requires token/user/business access to those pages.
See real sends per segurador                   Prefer SB/DigitalTrChat/ChatPion data.
Detect app down/inaccessible                   Yes via Graph API failures and token checks.
Detect developer account blocked              Usually by effect/error; not guaranteed as a single endpoint.
```

Being admin of a Meta app does **not** automatically grant access to every page owned by every segurador added to that app. App-level monitoring and page-level analytics are separate access models.

## 1Password Item Standard

Use one 1Password item per app.

Canonical item title pattern:

```text
BOT B001 Token
BOT B002 Token
...
BOT B010 Token
BOT B011 Token
```

Required fields:

```text
Field         Purpose
------------  ----------------------------------------------------
app_id        Meta app ID.
app_name      Human app label, e.g. B007.
access_token  User access token generated by an admin/dev user.
expires_at    Human-readable expiry date/time.
app_secret    App secret, only for token debug/exchange; never print.
notes         Site/block assignment, e.g. openzed e sub dominios.
```

Security rules:

- Never paste tokens, app secrets, or authorization URLs with returned codes into Discord.
- Never print secret field values in logs or final reports.
- Report only item title and lengths, e.g. `access_token len=194`, `app_secret len=32`.
- If a field was accidentally named `secret_key`, use it only as a backward-compatible alias and rename it to `app_secret` when possible.

## Minimum Permissions

For app-level health/rate-limit monitoring, start minimal:

```text
public_profile
```

For broader diagnostics used in MGS B001–B011 monitoring, these are acceptable:

```text
pages_show_list
pages_read_engagement
business_management
public_profile
```

Do **not** request write/send permissions for monitoring unless Rodolfo explicitly asks and the scope is justified:

```text
pages_messaging
pages_manage_metadata
pages_manage_posts
ads_management
```

## Token Creation Procedure

For each app, Rodolfo/admin can use Meta Graph API Explorer:

1. Open `https://developers.facebook.com/tools/explorer/`.
2. Select the target app, e.g. `B007`.
3. Select user token, not page token, for the first app-health monitor.
4. Add only the agreed read/diagnostic permissions.
5. Click `Generate Access Token`.
6. Test:
   - `GET /me`
   - `GET /app`
   - `GET /{APP_ID}?fields=id,name`
7. Save token in 1Password as `BOT B007 Token` or matching app number.
8. Do not send token screenshots or token text in Discord.

## Validation Command Pattern

Use `.env` with `set -a / set +a` because 1Password subprocesses need exported variables in cron/system contexts.

```bash
cd /root/mgs-agent
set -a
source .env 2>/dev/null || true
set +a
```

Recommended validation checks:

```text
Check                         Endpoint / Method
----------------------------- -------------------------------------------------
Token basic identity           GET /me?fields=id,name
App metadata                   GET /{app_id}?fields=id,name,category,link,app_domains
Token health/scopes            GET /debug_token with app_id|app_secret
Business visibility            GET /me/businesses?fields=id,name,verification_status
Visible pages                  GET /me/accounts?fields=id,name,category,tasks
Rate-limit usage headers       Read X-App-Usage from every Graph API response
```

Never print raw response fields that may contain tokens, page tokens, app secrets, or user secrets.

## Headers and Thresholds

Read these response headers from Graph API calls:

```text
Header                         Meaning
------------------------------ ------------------------------------------------
X-App-Usage                    App-level usage: call_count, total_cputime, total_time.
X-Page-Usage                   Page-level usage when a page token/endpoint is involved.
X-Business-Use-Case-Usage      Business use-case usage where Meta returns it.
```

Suggested alert thresholds:

```text
Usage %        Severity       Action
-------------  -------------  -----------------------------------------
<70%           OK             No alert, log only.
70–84%         Atenção        Watch app and delivery symptoms.
85–94%         Risco          Alert Rodolfo; reduce load if persistent.
95%+           Crítico        Alert immediately; consider splitting app/load.
API failure    Crítico        App/token/developer access may be broken.
```

For B007/Openzed, use a stricter operational posture because Openzed is the highest-revenue site:

```text
B007 >=85% or repeated API errors → immediate alert to Rodolfo.
B007 >=95% → recommend split Openzed into two apps unless transient.
```

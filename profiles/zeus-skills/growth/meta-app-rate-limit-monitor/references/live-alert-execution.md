# Live alert execution and contention recovery

Use for requested live deliveries across generic app routes and the dedicated DTR route. Keep credential gates, pause policy and delivery-only reporting in SKILL.md; use the native renderers rather than constructing replacement cards.

## 1. Prepare the request before launching writers

1. Freeze the current registry cohort, exact destination IDs, pause sets and latest message ID in each channel. Give the request a credential-free receipt directory and bind it to the actual source message and thread.
2. Inspect both canonical locks before starting. Resolve each runner's interpreter from its wrapper, including `PYTHON_BIN` or the native override for the dedicated runner; do not assume the generic Python process is the dedicated execution environment.
3. Estimate lock wait, full scan and enrichment separately from recent completed runs and the live target population. The dedicated DTR body iterates grouped credentials sequentially; its cron interval is not a runtime estimate. When that total may exceed the foreground ceiling, start one silent tracked process with bounded waiting from the outset and consume it before closing the task.
4. For generic fleet delivery, leave `MGS_META_APP_ROLE_ITEMS` unset, set `MGS_META_APP_ROLES_FORCE_LIVE_ALERT=1`, and pass the canonical state and pause paths. For the dedicated route, set `MGS_B013_DTR_FORCE_LIVE_ALERT=1` and its canonical state path. Keep snapshot mode disabled and preserve all source reads and native reconciliation.
5. Handle an explicitly requested paused destination as a separate one-off stage under the generic lock. Copy the current pause document to the request's receipt directory, remove only that requested key from the copy's `apps` and `monitor_apps`, set `MGS_META_APP_ROLE_ITEMS` to its exact registry title and point `MGS_META_APP_ROLE_ALERT_PAUSE_PATH` to the copy; keep the canonical state path. Never edit canonical containment to make a resend execute. If fresh reads confirm restriction, use the native restriction renderer rather than snapshot mode. When its normal daily cooldown would suppress this explicitly requested notice, the isolated stage can set `MGS_META_APP_ROLES_API_BLOCKED_ALERT_COOLDOWN_MINUTES=0`; never persist that override or reset stored cooldowns. Compare the canonical pause document before and after the run, and report a restriction notice separately from a live-metric alert.

## 2. Resolve contention without replay

1. Preserve the scheduled writer. Inspect its owner, elapsed time, current job claim and persisted target-specific timestamps before declaring a stale lock or failed schedule.
2. If the PID from `/proc/locks` is absent from the visible process namespace, identify visible holders by matching the lock file's `st_dev` and `st_ino` against `/proc/<pid>/fd/*`; then inspect the matching visible PIDs and parents with `ps`. An unsuccessful direct PID lookup does not prove the lock is stale. An open descriptor alone does not prove ownership: distinguish the established writer from a waiting requester using its job claim, elapsed time and stage receipts.
3. Distinguish **waiting for the lock**, **body entered**, **fresh receipt persisted**, and **delivery read back**. Write a before-run stage receipt only after acquiring the lock. If the wait expires before entry, confirm that absence and inspect channel messages before another attempt; a missing final receipt alone does not establish zero side effects.
4. After zero side effects are established, resume only the undelivered runner with one bounded waiting process under its existing canonical lock. Acquire that lock once and execute the unchanged embedded body with its native interpreter; never invoke a self-locking wrapper while holding the same lock. An empty preflight lock listing does not reserve the lock: a scheduled writer can enter before launch. For the dedicated Bash runner, a request-local copy can replace `flock -n 200 || exit 0` with `flock -w <bounded-seconds> 200 || exit 75`, then write the body-entered timestamp immediately after successful acquisition. To capture completion under that same lock, remove only `exec` from the Python invocation in the copy, retain its interpreter and embedded body, and append a copy of the canonical state plus a completion timestamp after successful exit. Preserve `set -euo pipefail`, both environment-source steps and the canonical lock path; never edit the production runner or schedules merely to wait for this delivery.
5. Treat a process-wait timeout as an observation window ending, not as operation failure. Continue observing the same process while it runs; do not launch a replacement writer. Preserve and verify the already-delivered generic routes while the dedicated route waits or scans.
6. If contention materially delays completion, tell Rodolfo briefly which destinations are complete and which route is still waiting or collecting. Finish with the actual result, not a promise of an untracked retry.

## 3. Verify each requested family independently

1. Require a fresh run receipt and an actual process exit. Copy each stage's summary before releasing its canonical lock, because the next scheduled run can overwrite the shared latest-summary field. For generic routes, compare the completed processed-item set against the frozen registry cohort minus full-route pauses, then verify any explicitly requested paused keys through their separate one-off stage. For the dedicated route, use its own fresh account/link summary, not generic app roles.
2. Read messages newer than each saved channel baseline, paginate if necessary, then GET the exact native card object. Also require that card to be later than this runner's lock-acquired/body-entered timestamp: a baseline can fall between a scheduled card and its continuation tables, so post-baseline messages alone do not prove requested delivery. Match the current app generation and requested-live description, or the fresh native restriction notice for a blocked route, and isolate that card's continuations from later scheduled families.
3. Parse section headings across every continuation code block, carrying the current section across message boundaries. Count six-column data rows rather than messages or repeated headers: a later chunk may contain no header. Validate money cells and compare current-user counts with that run's operational roles or dedicated `linked` count. Use the native pending-section equivalent for each runner. If the pending table has fewer rows than the fresh summary, inspect its renderer before diagnosing transport loss: native formatters can deliberately slice the input list. Verify the deployed limit rather than hard-coding a remembered value, and record both total pending and displayed pending in the receipt. Matching the formatter's cap proves native-output delivery, not complete pending-population coverage; disclose material truncation instead of silently redefining the expected total or resending an already-landed alert.
4. Require one complete requested logical message family per destination and state separately whether its population tables are complete or renderer-limited. Do not hard-code three physical messages; large account tables split into additional continuations. Aggregate and deduplicate counts in code before claiming complete coverage. Take reported membership and pending totals from this request's captured completed summary, not a preceding cron-status answer, because links can change during collection.
5. Repair validator-only mistakes without resending landed alerts. If only one route remains undelivered, recover only that route. Preserve completed destinations, pauses and the sole writer.

## 4. Close with request-sized reporting

Persist final delivery receipts and clear pending execution stages. Report verified delivered/requested channels and freshness in one or two sentences; mention a recovered delay or material caveat without turning an alert-only request into a fleet audit. Keep detailed counts, runtime traces and proof paths in the receipt rather than the executive reply.

# Read-only app-to-Business ownership verification

1. Resolve the exact active app and immutable 1Password item from the registry. Keep credentials only in process memory; verify app identity with `GET /{app_id}?fields=id,name` and the app access token.
2. Do not assume SDK-listed Application fields are exposed by the deployed Graph version or token context. If `business` or `owner_business` returns code 100/nonexisting field, stop retrying those field variants and switch to the Business ownership edge. An unsupported field does not establish that the app has no BM.
3. Read the existing app-admin user token from the same approved item; inspect `debug_token` for validity, app binding and `business_management`. Never rotate credentials or substitute an unrelated account to answer the lookup. A scope/visibility denial is an inconclusive ownership lookup, not proof of no owning Business.
4. Fully paginate `GET /me/businesses?fields=id,name` with that user token. For each returned Business, fully paginate `GET /{business_id}/owned_apps?fields=id,name` and retain only exact requested app-ID matches. Consume pagination internally; never print `paging.next` or raw token-bearing URLs.
5. A matching `owned_apps` result is positive evidence of ownership. `client_apps` proves shared/accessed apps, not ownership. If no match is found, qualify the result by the token's visible Business scope rather than declaring global absence.
6. Return the exact app ID/name and confirmed owning Business ID/name, with the read-only scope. Project every response to these fields before printing or saving it; do not expose unrelated Business assets or credentials.

## Restriction versus messaging-delivery diagnosis

- Read `/{business_id}?fields=id,name,verification_status` with the existing scoped admin token, but never translate `verified` into “unrestricted”: business verification and enforcement status are separate facts. The public Business field set may not expose the Business Support Home restriction verdict.
- Treat app `/permissions` values of `live`, valid user tokens, visible pages and successful subscriptions as independent capability checks, not proof that a Drip or Broadcast message was delivered. A primary app-admin token can legitimately return zero `/me/accounts` pages even when operational seguradores expose pages; compare the actual affected profiles rather than infer a fleet collapse from that admin alone.
- For a bounded affected-profile sample, verify exact DTR login and account identity under the canonical monitor lock. In the account selector, deduplicate repeated DOM representations by immutable account ID and normalized name; distinct IDs with the same name remain ambiguous. Match the deployed native optional-CSRF request contract rather than inventing a required field in a custom probe.
- Use the official Page Integrity API `GET /v24.0/{PAGE_ID}/page_status` with each Page's own token and granted `pages_manage_metadata`, excluding globally ignored Page IDs. This read was validated against actual Page responses. Project `status`, active `restrictions` (especially `page_messaging` and `page_messaging_api`) and violation types. Stop cohort replay on an unsupported/denied edge; failure is not a clean integrity verdict. Keep the request's API version isolated from production configuration.
- Distinguish per-Page `status=ok` with empty restrictions from a Business-level enforcement verdict, and disclose the exact sampled profile/page population. Do not extrapolate a clean sample to the entire app.
- Inspect existing DTR Campaign Report evidence without resending or retrying messages. Separate sent, delivered and opened counters; completed status alone and postback-trigger counters do not establish user-message delivery. Historical DTR delivery can predate a token/app reauthentication, so do not claim it exercised the current credential binding without matching timestamps and execution evidence. A visible ten-row table is a sample unless its full pagination was traversed.
- State any remaining Business Support Home enforcement or concrete send-error gap explicitly. Do not recommend moving the app, reauthenticating every profile, changing permissions, or sending production tests from verification/capability evidence alone.

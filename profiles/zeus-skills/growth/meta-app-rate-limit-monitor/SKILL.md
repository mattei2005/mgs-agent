# Meta App Rate Limit Monitor — MGS

## When to Use

Use for app replacements, rate-limit/token health, segurador membership or DTR-link audits, Sheet reconciliation and current app-channel alerts. Resolve generations from the registry: generic role-based lineages and the dedicated B013 DTR/ChatPion lineage have different evidence and runners.

## Always-on operating contract

- Resolve the active app generations and destinations from the live registry. Treat the B001–B012 lineages as role-based and the B013 lineage as the dedicated DTR/ChatPion route; never infer current generations from historical examples.
- Treat Rodolfo's new, exact completed replacement report (`old→new`) as authorization to validate, update and reactivate that same existing monitor route. Preserve its channel, runner and unrelated pauses; require preflight, backup, fresh app-scoped state, silent baseline, clean repeat and readback. This does not authorize credential rotation or broader changes. In `references/route-pack-05.md`, start with **Replacement-report authorization**, **Replacement credential identity and concurrent onboarding**, and **Scoped replacement writes and closure readback** rather than loading the historical cutover narratives.
- During replacement preflight, distinguish the 1Password record ID from the Meta app ID: an operator may update the same vault record in place. Read its current exact title and `app_name`, compare the new Meta app ID against the predecessor's saved monitor snapshot, and verify the token's app binding; an unchanged vault-item ID neither blocks migration nor proves app identity. If the declared replacement still contains the predecessor's Meta app ID, stop before registry/state writes or unpausing; diagnose that exact ID with live metadata and `debug_token` reads and report the confirmed mismatch. A renamed item or migrated Sheet does not prove that its credential fields were updated. If the holder updates only `access_token`, distinguish token validity from the configured `app_id`/`app_secret` pair: first read `/me`; if configured app authentication fails, try read-only `/debug_token` with the new user token as both `input_token` and authentication token, only where Meta permits that holder to inspect it. A successful response can independently establish `is_valid`, `app_id` and `application`; a denied response remains inconclusive. Verify the returned application matches the declared replacement, then test its returned app ID with the existing secret only in process memory against metadata and `debug_token`. An invalid-signature response proves that pair does not authenticate, not that the new user token is expired. Report exactly which fields still disagree; preserve containment and ask the holder to correct the same item. Record the discovered ID in credential-free diagnostic evidence, but do not promote it into production credential fields or the active registry, alter secrets, unpause or complete cutover before the normal credential gate passes. Never try to recover predecessor credentials by reading that already-updated item.
- Derive replacement `expected_sheet_roles` from fresh Service Account `NO APP` assignments after checking predecessor residues and composed-identity completeness/uniqueness. Do not inherit the predecessor's expected count or restore its former assignments merely to match it: the authorized migration can legitimately change the assigned population.
- Handle consecutive replacement reports in one thread as distinct, narrowly scoped cutovers. Before each one, refresh the registry and both pause sets; bind its checkpoint, backup and receipts to that report's message ID while retaining the actual conversation thread ID. Preserve earlier validated replacements and unrelated pauses: the original thread topic is not the target selector, and a preceding cutover's pause snapshot is no longer the current baseline. When the holder confirms correction of a blocked replacement's existing 1Password item, resume that same authorized checkpoint: reconcile partial effects, rerun the complete credential gate, then finish the pending canary/baseline/reactivation and scheduled readback without asking again or stopping at token validity alone. At closure, supersede active blocker fields and next steps in both checkpoint and inventory; retain failed checks explicitly as historical evidence so an old credential hold cannot revive.
- Prove actual execution from a target-specific `checked_at` later than the unpaused manual receipt and a completed full-scope summary, not the scheduler's `last_status=ok` alone: native non-blocking lock wrappers can exit successfully without scanning. For the generic scheduled cycle, derive expected item titles from the current registry excluding B013 and full-route `monitor_apps` pauses; require exact set equality with `_last_run_summary.processed_items` and zero errors. Do not hard-code the fleet count or exclude alert-only pauses: each reactivation changes the processed population. Observe the persisted result with a bounded foreground wait rather than starting another writer. While a manual writer holds the canonical lock, treat scheduled skips as skips, preserve the existing writer and consume its result before considering a retry.
- Close a replacement with a fresh target-specific scheduled-cycle receipt and fresh Service Account Sheet parity, not only a successful manual invocation. Use that latest verified cycle for the final present/assigned count: acceptances can legitimately increase during onboarding. Verify any resulting native automatic alert and its complete user table; do not force an extra alert just to demonstrate reactivation. Compare pause sets before/after and remove only the authorized predecessor/replacement containment.
- Interpret a recheck as fresh verification, not permission to resend alerts or rewrite healthy monitors. When Rodolfo explicitly requests **check first, then send real alerts to all apps**, finish the verification before publication and verify the new delivery in every requested channel before answering. For **send updated alerts to all channels**, execute the native force-live routes with fresh source reads and complete delivery readback; do not expand this into a separate fleet audit or rewrite healthy configuration. Reconcile screenshot channel labels with live channel IDs and registry generations, not stale stored channel names.
- Keep monitor-only requests with Zeus: verify scheduled source reads, reconciliation and any genuine automatic delivery rather than turning account gaps into a default handoff to Ially or another operator. Contact an operator only when requested or covered by an existing explicit handoff. If Rodolfo declines a handoff, remove it from the task's next steps and close with the verified monitor verdict; do not re-ask the same handoff or imply that updating the monitor requires every profile to be reconnected.
- Freeze composed target identities and the source capture time for each validation cohort during live onboarding. Verify a completed native cycle and fresh Sheet parity for that cohort; classify assignments added after the cutoff separately as awaiting a subsequent cycle, not as failed collection. Do not keep expanding the acceptance set as new rows arrive, because a completed scan cannot contain targets assigned after its source snapshot. Investigate a frozen target that remains absent after its applicable completed cycle; never use the cutoff to hide a genuine omission.
- For a historical alert audit, resolve the requested civil-day boundaries in the operational timezone, including daylight-saving offset changes, then paginate the complete channel window. Count logical alert families, Discord messages, movement occurrences and unique affected profiles separately. Parse movement sections separately from current-user and cumulative-removal tables; repeated cumulative rows are not new incidents. Compare each reported removal or disconnection against fresh source evidence before calling it genuine or duplicate, and leave the initiating actor unattributed unless evidence identifies it.
- Keep app health, individual membership/link status, investment availability and revenue separate. A healthy app can still have assigned profiles awaiting entry or reconnection; report those profiles without calling the app restricted or claiming that every profile is connected.
- For B013, preserve the last confirmed connection verdict separately from fresh diagnostic observations. An unknown/read-failure→linked recovery is not a new member without a confirmed prior disconnection; a new canonical Sheet assignment is a separate monitoring-scope event. Deduplicate movements by composed identity and confirmed transition, never by event counts alone. Keep unknown observations fail-closed without carrying stale successful token/page fields into them. For a single profile's persistent Sheet X or reported reauthentication, verify that exact composed identity with a fresh native DTR/Meta probe under the canonical lock; compare its observation time, not the full cycle's completion time, with the reported change. Clear only its exact marker after a valid current-app link and read back the cell; preserve the fleet state and ordinary scheduled movement alerts. Use `references/b013-confirmed-link-transitions.md` for the focused recheck, audit and regression procedures.
- Interpret `INVEST HOJE` and `INVEST 3D` as spend, not revenue. `n/d` is unavailable data or an unmatched profile, never proof of zero revenue. Show numeric zero only when the source explicitly provides it; label today's totals as partial and use the preceding three completed dates for the three-day metric.
- Convert timestamped Smart Bidding `finalDate` to the monitor's operational `America/New_York` civil date before selecting today's partial spend and the prior three completed dates. Never slice a UTC ISO timestamp as a date or fall back to the latest returned row: UTC can already be tomorrow while the operational day is still today, but a genuinely missing required date must remain unavailable. Cover summer/winter offsets and actual local midnight in regression tests; validate both real consumer loaders without forcing a new Discord alert.
- Preserve the last requested investment enrichment receipt separately from the latest lazy cycle: `not_requested` must not erase the failure or recovery evidence. Retry one transport/timeout/5xx failure only; keep unavailable data as `n/d`, never zero-fill it. Do not immediately retry authentication, rate-limit or invalid scope/date contracts. Retain only allowlisted error classifications, never raw browser output or credential-bearing URLs. Resolve each consumer's interpreter from its native runner before building a custom probe, then require regression tests and a real loader call through that execution environment; fixture success alone does not prove browser-wrapped output parses. If the historical failure was overwritten and is no longer reproducible, state that limitation rather than inventing its root cause.
- For a requested live resend, check app metadata and fully paginated `/roles` first, then evaluate the admin token separately. When those app reads succeed but `/me` or `debug_token` fails, use the native force-live renderer with its explicit admin-token warning; do not suppress the requested real alert solely because the admin token is unhealthy or claim complete health after delivery. Distinguish expiry (OAuth 190/463) from a login/security checkpoint (190/459); renewal or holder verification is a separate credential dependency, never permission to rotate credentials, re-add memberships, or label the app deleted/restricted. Verify the warning in the exact delivered embed and every continuation message. Preserve unresolved members by their actual Graph IDs, report their count, and never invent names or infer removals from failed identity resolution. Keep raw Graph member count, resolved identities, current Sheet assignments and pending markers separate: unmatched IDs can make a member/assignment ratio misleading. When a screenshot contradicts the alert, compare the exact app ID and complete visible names with a fresh, fully paginated Graph result; preserve a UI-present/API-absent member as a discrepancy, not a confirmed removal. After token renewal, resolve unknown IDs again and compare the names independently of the total: successful identity recovery does not explain a remaining UI/API count difference. Do not assign screenshot names to unresolved IDs by elimination. Close with delivery confirmation and the material token/identity caveat, requesting holder action only for the unresolved credential dependency.
- For a fleet token-expiry check, freeze the current registry cohort and inspect each primary configured token read-only with metadata, `/me` and `debug_token`; do not run full role/Sheet reconciliation or send alerts merely to answer an expiry question. Include paused lineages in the audit without resuming them, and report an in-place renamed item separately from its still-active registry predecessor. Persist credential-free batch receipts and require exact cohort coverage before declaring totals. Separate confirmed expiry, valid app-bound tokens, holder checkpoints, and app-authentication/binding failures; never count an inconclusive token as healthy. Interpret `expires_at=0` only as no scheduled expiration reported, not immunity from revocation; show a future nonzero expiry in the operational timezone. State the primary-token scope rather than implying backup credentials were also tested.
- Explain corrections plainly: a repaired generator does not retroactively update Discord messages already sent. Distinguish old messages from newly requested alerts, and do not imply that a paused route will publish a replacement automatically.
- Treat an explicit resend to every app as delivery scope, not permission to reactivate contained routes. For a requested paused app, use a scoped one-off native check/notice while preserving canonical pauses. If fresh Meta reads confirm restriction, deliver the native restriction notice instead of a stale user table; count it separately from successful live-metric alerts. Verify both destination coverage and unchanged containment before closing; use `references/live-alert-execution.md` for execution details.
- Match the closing report to the request. For alert delivery only, confirm the programmatically verified delivered/requested channel count and freshness in one or two sentences; mention only material pending work or recovered delivery issues. For a routine replacement, report the new label, preserved route, scheduled health and latest present/assigned count with remaining onboarding gaps; do not turn it into a fleet audit. For audits, use numbered findings with **Problema, Causa e Solução**, distinguish confirmed causes from unavailable historical evidence, and separate monitor health from named membership/link gaps and source-unmatched investment rows. Keep technical traces and proof files out of the response unless requested.

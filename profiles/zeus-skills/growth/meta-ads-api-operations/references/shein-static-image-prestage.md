# SHEIN static images — central maintenance and operational handoff

Use the existing `ares-shein-campaigns.py` grouped-manager route. Behavioral permission for generic media is not proof that the deployed compiler/uploader supports the requested format; trace intake → pre-stage → registry → schema/prevalidation → compiler → semantic/rendered QA → inventory → status-only activation before changing a validator.

## Installed routing

- Canonical SHEIN `IMG` PNG/JPG/JPEG is a static image, never a video derivative. `VID` remains MP4. Preserve exact filenames, ordered groups and literal copy.
- `ares_campaign_v3.image_prestage` uploads on the exact account's `adimages` edge using the same registered credential. No Page-video upload, personal identity, guard expansion or alternate campaign writer.
- Registry identity remains account + asset + clean checksum. Image records carry `media_type=image`, `image_hash`, `upload_edge=ad_account_adimages`, readiness and verified account association; legacy video records retain their original shape/defaults and video-only consumers reject image records.
- Images compile as `object_story_spec.link_data.image_hash`, preserving source identity/CTA and approved destination/tracking/copy. For `clone_prestaged`, explicitly supply exactly one `media_sourcing_spec.images` entry with the SAME `hash`, `source=multi_media`, `opt_in_status=opt_in`, and the literal title/body/description. Omitting sourcing on Ad Copies can leave the source video's sourcing incompatible with the image and produce `100/4931013`; do not send the image hash as a video ID or reuse source videos/related media. Meta's official multi-media contract requires the primary story media to appear in sourcing.
- Reconciliation and semantic QA require the exact image hash, including core creative recovery matching. Rendered QA requires actual static image media, not a playable source video or a link-only preview. Existing all-campaign PAUSED QA and central `activate_verified` gates remain unchanged.

## Readback-first image recovery

1. Verify the original bytes by SHA256, Drive MD5/size, clean metadata, static format and current manager-folder/lineage authority before upload. Confirm current Drive MD5 again during handoff.
2. Reconcile the exact account image library by deterministic filename (`V3 IMAGE {asset_id} {checksum-prefix}{extension}`), with complete pagination and no ambiguity. Image names are limited to 100 characters.
3. Persist an upload intent before POST; persist the response hash before readiness commit. After a lost response, resolve that same deterministic filename/hash. An unresolved prior intent blocks replay; never upload again blindly or treat a timeout as proven zero effect.
4. Never persist signed Meta image URLs or use them as creative identity. Use the account-library hash and direct readback; preserve use/test history and the manager's physical folder. No implicit deletion or cleanup.
5. If a hash changes or Meta retains source video fields, fail closed PAUSED and reconcile the same request/IDs through the core. Do not weaken QA to make the first image request pass.

## Materialized image names are auxiliary, not hash identity

- Keep `require_image(..., name=...)` strict by default. Do not whitelist `_105`, numeric suffixes or arbitrary renamed names by pattern. A changed label alone neither authorizes upload nor proves image lineage; the origin of an observed suffix remains unproven without evidence.
- For an already confirmed upload, central `image_identity.require_prepared_image` may supersede the label only after exact account/hash/asset/full-SHA256 identity agrees across the ready associated `ad_account_adimages` registry record, the canonical preparation and its unique asset, the exact deterministic upload-intent path and unchanged `READY` receipt. Verify the actual local static bytes, SHA256, Drive MD5, dimensions, active status and any available caller Drive identity. Missing/ambiguous receipts, changed bytes/dimensions/hash/account/lineage, mixed VID identity or missing active status fail closed. Never rewrite the Meta label, registry, intent, input or sealed manifest to manufacture agreement.
- Apply the same bound lookup before grouped reservations, on pre-stage cache hits, in handoff and before postprocess. A known but invalid registry record is not a cache miss or permission to reupload. An unresolved/lost-response intent without a confirmed hash remains blocked; do not discover it from a suffix. Preserve deterministic-name ambiguity checks for unbound discovery.
- Maintenance validation must exercise real read-only cache hits with upload/receipt writes hard-prohibited, full `load_ready_assets`, Drive MD5/size against local bytes, fresh account-library exact hashes and the same existing PAUSED IDs. Use an authentic existing Ares worker environment without synthesizing `HERMES_PROFILE`; record module origins. Offline integration must include rename → prepare/recovery → handoff → finalize, repeat idempotency, and missing/ambiguous library negatives proving no new upload or reservation before failure. A renderer startup test can observe an existing empty `DevToolsActivePort` file; preserve that failure, rerun the complete unchanged acceptance suite, and route readiness hardening separately rather than excluding the rendering gate or changing unrelated production code inside identity maintenance.
- Release only the original typed continuation to the owning Ares after installation under account/request locks, backup and installed regression/live readback. Read-only maintenance does not run final postprocess/activation or prove ACTIVE/serving.

## Sealed-manifest sourcing recovery

- Reconstruct the failed request body from the sealed slot, confirmed adset ID and exact copy parameters; compare its digest to the durable write journal before attributing the failure. Error `4931013` proves primary story media is missing from sourcing; source-sourcing inheritance is an implementation inference unless directly exposed by Meta.
- Never regenerate, edit or reseal a manifest after partial campaign creation just to add sourcing. The central `image_sourcing.resolve_operations` supports legacy sealed IMG slots with recipe `shein-static-image-sourcing-v1`: validate operation/account/mode/PAUSED status, source/slot/hash/checksum, exact payload and target adset; fresh GET the exact PAUSED campaign/adset and complete zero-ad edge; persist the immutable slot receipt BEFORE central transport submits the effective payload. The receipt binds sealed-manifest/creative digests, effective digest, slot/idempotency key and live IDs. The original manifest, request, schedule/SLA and reservations stay intact.
- Extra GET points are reserved centrally. The same resolver covers missing ads in the existing bundle and unattempted bundles; it never copies campaign/adset shells during recovery. A dry-run discloses the recipe/legacy-slot count but does not prove live zero-ad readiness or Meta acceptance. Diagnostic receipt copies in maintenance workspaces are not executable manifests or installed production checkpoint updates.
- Fail closed on any existing ad, pagination, unknown/changed account/parent/status, missing journal, changed receipt or altered immutable identity; do not bypass that guard to replay a partially successful correction. Reconcile through the core before a further recovery. Already resolved/terminal slots retain existing idempotency behavior.
- Query `media_sourcing_spec` in consolidated, runner and activation readbacks. Semantic QA rejects wrong/extra image hashes, videos, related media, literal-copy substitutions and unapproved customizations. The status-only activation barrier independently rechecks image sourcing and compares it to the verified PAUSED proof, blocking drift before any ACTIVE POST.
- When real pre-stage and request-ready already exist, resume only the SAME canonical `campaign --input <existing-request-ready> --dry-run`, then the owning Ares execution after maintenance closure. Do not rerun uploads, reserve new assets, substitute IDs, or retry the old effective payload unchanged. Keep historical batches outside the request untouched.

Official contract: https://developers.facebook.com/documentation/ads-commerce/marketing-api/ad-creative/multi-media-ads . Regression owner: `tests/test_shein_image_sourcing.py` plus existing image/VID, media-QA and activation suites.

## Exact reviewed targeting on an existing IMG batch

- Treat a resolved material review as separate evidence, never as a replacement for the original request/source message or a generic targeting normalization. Use a typed continuation through `shein_continuation`/`shein_reviewed_targeting`; bind the exact request, account, source, all campaign/adset/ad IDs and lineage, both sealed manifests, original execution clock, resolved same-day intent and native-copy schedule receipts.
- Verify original message, precise question, explanatory context and real human reply by fresh Discord GETs, including author, content, edit state and reply linkage. A technical seal is not permission: preserve the owning runner's live channel-authority checks and existing QA/activation gates.
- For a reviewed age-unknown plus device omission, compare the entire expected targeting after only those exact approved transformations. Reject extra/missing flags, age/geo drift, other requests/IDs/reviews and every unbound field; keep historical reviews isolated.
- When the original instruction explicitly changes the bid, compare target bid and constraints with the sealed approved manifest, not the source campaign's old bid. This does not authorize any new bid/budget write or manifest reseal.
- Validate the installed descriptor read-only in Ares with the common guarded transport and negative tests before handoff. Maintenance must not fabricate QA proof, run campaign recovery/activation, repair targeting, upload or reserve; Ares resumes the same central `ares-shein-recovery.py --continuation <installed-descriptor> --confirm-execute` and owns semantic/rendered QA and final ACTIVE readback.

- The campaign owner must still run real `prepare-media --input <original-request> --confirm-execute`, then `campaign --input <request-ready> --dry-run`, then the authorized central execution. Require all exact images/texts, requested budget/bid/schedule, all rendered previews, and final GET readback before announcing creation/ACTIVE. Preserve original timing and canonical same-day elapsed-start policy rather than editing the intake.
- Keep maintenance separate from the campaign transaction. Stage and test the complete package, check concurrent source/writers, preserve rollback, publish coherently, re-test installed files, and record inventory/audit/REPORT-INFRA. A deferred historical checkpoint is not permission to modify or replay it.

## Native-code reproduction — synthetic credentials, no production writes or HTTP

Runtime investigated: /root/.hermes/hermes-agent-stage-main-7cc3fb8c-mgs.

The reproducible probe mocks token-endpoint responses, auth-store mutation and socket connection. Its results are software behavior tests, NOT real OpenAI responses.

1. Baseline normal expiry plus a successful simulated token response: native selection performs one refresh and returns the rotated token. Expiry alone does not explain an unrecoverable login.
2. Stale manual pool instance after a peer rotated its same persisted row: native code POSTs the consumed old refresh token instead of rereading that row. Probe: one POST, no peer adoption, row marked dead. Expected: zero stale POSTs and adoption of the peer's persisted generation. Production has this defect; this probe does NOT establish that the historical incident actually contained such a peer rotation.
3. `refresh_token_invalidated` classification: simulated OpenAI session-ended response is not terminal in the deployed classifier. Native row becomes exhausted without retaining the error reason/message. Candidate correctly marks dead and retains reason/message. The historical Ares message matches the wording; the exact upstream code was not retained, so do not describe that historical code as captured.
4. Low-level pool fallback: an expired, exhausted pool row is returned as usable because no access expiry/dead/exhausted guard is applied. Probe returns an expired bearer. This is consistent with Zeus's observed token_expired request after pool exhaustion, but is not a wire trace of that request.

Files: agent/credential_pool.py `_refresh_entry`, `_sync_entry_from_pool_store`, `_recover_failed_refresh`; hermes_cli/auth.py `OAUTH_PROVIDER_FLOWS`; hermes_cli/auth_codex.py `_pool_codex_credential`.

## Exact remaining evidentiary gate

No surviving production evidence identifies what first invalidated the old refresh grants. Reproducing client defects does not identify who revoked an OpenAI session. No current token was force-refreshed and no historical refresh token was spent during diagnosis.

A controlled real token-renewal test can establish whether a newly issued grant is renewable now or is already rejected on its first attempted refresh. It may rotate production credentials and therefore requires Rodolfo's explicit Critical Subset confirmation. Run one target at a time, with protected backup, precise credential targeting, native locked writeback on success, safe response-code/request-ID capture, and immediate exact-marker inference validation. Do not clone token stores, switch accounts/providers, weaken controls, replay stale snapshots or promise that a current successful refresh proves the old revocation origin.

The preceding gate was pending as of the initial report. It is superseded by the approved test below. Candidate is still not deployed; no service restart was performed.
